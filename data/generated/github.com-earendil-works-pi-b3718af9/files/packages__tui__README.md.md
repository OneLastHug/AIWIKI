## 核心流程

作为 README，它的核心流程不是“程序执行流程”，而是“读者理解流程”。一个健康的 `packages/tui/README.md` 通常应该按下面的路径组织信息：

1. 先说明 `tui` 包解决什么问题：把底层 agent/CLI 状态转换成可交互的终端界面。
2. 再说明它处在整体架构中的位置：上游接收 CLI 启动参数、会话状态、模型输出和用户输入；下游驱动终端渲染、键盘事件、滚动、布局和状态更新。
3. 然后给出开发入口：如何安装依赖、如何启动交互模式、如何运行检查或局部测试。
4. 最后说明修改边界：哪些文件是 UI 行为核心，哪些只是样式、文案或示例，哪些改动会影响包 API 或发布行为。

根据仓库规则中的 TUI 测试说明推断，交互模式的验证流程可能依赖 `tmux` 启动测试会话、运行 `./pi-test.sh`、捕获 pane 输出，再发送 prompt 或特殊按键验证界面行为。这说明 TUI 的真实风险点不只在类型检查，还包括终端尺寸、按键序列、异步流式输出和渲染稳定性。

## 关键函数的高层作用

`packages/tui/README.md` 本身没有关键函数。若把它当作包入口文档，它应该帮助读者识别包内真正值得关注的核心函数或模块。根据当前片段推断，`packages/tui` 这类包的关键实现通常会落在以下几类：

- TUI 启动入口：负责初始化终端环境、挂载渲染树、连接会话状态，并在退出时恢复终端。
- 输入处理逻辑：把键盘事件、快捷键、粘贴、多行输入等转换成应用动作。
- 渲染/布局组件：根据终端宽高、消息列表、输入框、状态栏等状态计算最终显示内容。
- 会话状态桥接：接收 agent 或 CLI 产生的流式事件，把模型回复、工具调用、错误、取消状态映射到 UI。
- 清理逻辑：处理 Ctrl+C、退出、异常、终端恢复和异步任务取消。

辅助函数一般只负责格式化文本、截断宽度、计算颜色、处理边框或状态标签；这类逻辑修改时要关注显示边界，但不应扩大成架构入口。

## 修改风险

修改这个 README 的直接运行风险低，因为它不参与编译和运行。但它属于关键文件页，文档错误会带来维护风险：

- 如果启动命令写错，开发者会用错误方式验证 TUI，导致交互回归漏检。
- 如果包边界描述不准确，后续改动可能把 CLI、agent 和 TUI 的职责混在一起。
- 如果遗漏终端交互测试要求，按键、布局、流式渲染、退出恢复等问题可能只在真实终端中暴露。
- 如果文档引用已不存在的路径或命令，会降低新贡献者定位问题的效率。
- 如果 README 被 npm 发布使用，错误说明会影响外部用户安装和使用。

更高风险来自 README 所描述的对象本身：TUI 包通常对异步事件、终端能力、窗口尺寸、输入法/粘贴、快捷键配置和进程退出都很敏感。修改相关实现时，不能只看静态类型；需要结合交互模式验证。根据仓库规则，代码改动后还应运行 `npm run check`，但该命令不等价于完整交互测试。
