# 目录：.husky

## 它负责什么

`.husky` 是这个仓库的 Git Hooks 配置目录，用来在开发者执行特定 Git 操作时自动触发本地校验流程。它不属于业务代码，也不参与运行时逻辑；它的职责更接近“提交前守门”：在代码进入提交历史之前，拦截明显不符合仓库规则的改动。

根据当前仓库的开发规则片段可以确认，这个项目对提交阶段有明确约束：提交前会阻止未经允许的 lockfile 变更，除非设置 `PI_ALLOW_LOCKFILE_CHANGE=1`；代码变更后要求运行 `npm run check`；提交时不能使用 `git add -A`、`git add .`、`git commit --no-verify` 等会绕过或扩大影响面的操作。因此，`.husky` 很可能承载了这些约束中一部分自动化检查，尤其是 `pre-commit` 阶段的校验。

从职责上看，`.husky` 不是“质量检查实现本身”的主要所在地。真正的检查逻辑通常分散在 `package.json` scripts、项目脚本目录、lint/typecheck 配置、测试配置、lockfile 检查脚本等位置；`.husky` 只是在 Git 生命周期里调用这些命令，把开发规范接入本地提交动作。

## 直接子目录地图

根据当前片段可确认目标路径为 `.husky`，但本次可见信息不足以完整列出其所有直接子目录和文件内容。因此这里按 Husky 目录的常见结构和当前项目规则作地图式说明。

`.husky` 目录通常较扁平，核心不是大量子目录，而是一组与 Git hook 同名的入口文件，例如：

- `.husky/pre-commit`：提交前入口，通常用于运行格式、类型、lint、lockfile 或生成物检查。
- `.husky/commit-msg`：提交信息检查入口，如果存在，通常用于限制 commit message 格式。
- `.husky/pre-push`：推送前入口，如果存在，通常用于更重的检查。
- `.husky/_`：Husky 自身辅助目录，在部分 Husky 版本中用于放置初始化脚本或兼容逻辑。

根据当前片段推断，本仓库最关键的直接成员应是提交前相关 hook，尤其是 `pre-commit`。依据是开发规则中明确提到“Pre-commit blocks lockfile commits unless `PI_ALLOW_LOCKFILE_CHANGE=1`”，这说明仓库提交阶段至少存在某种 pre-commit 自动检查。

## 关键入口

`.husky` 的关键入口不是 TypeScript 函数或类，而是 Git hook 脚本文件。Git 在特定操作发生时，会直接执行 `.husky` 下对应名称的脚本。

最重要的入口是：

` .husky/pre-commit `

这个入口通常发生在 `git commit` 创建提交之前。它适合放置成本较低、反馈直接、必须在提交前阻止的问题检查。结合本仓库规则，它可能关联以下事项：

- 检查 lockfile 是否被提交，以及是否设置 `PI_ALLOW_LOCKFILE_CHANGE=1`。
- 调用 `npm run check` 或相关轻量脚本，确保类型、lint、格式、生成物一致性等基础质量门槛。
- 拒绝某些不符合仓库规范的改动组合，例如直接修改生成文件而没有同步修改生成脚本。

可能存在的次级入口包括：

` .husky/commit-msg `

如果该文件存在，它会在提交信息写入后执行，适合检查提交消息是否符合 `{feat,fix,docs}[(scope)]: message` 这类格式。从当前开发规则看，仓库对提交消息格式有要求，但证据不足以确认该要求是否由 `.husky/commit-msg` 自动执行，也可能仅由人工规范或 CI 检查承担。

` .husky/pre-push `

如果存在，它会在 `git push` 前执行。通常用于比 `pre-commit` 更重的检查。不过当前开发规则强调的是提交阶段和发布阶段，未看到足够证据说明本仓库一定使用 `pre-push`。

## 主流程位置

`.husky` 的主流程可以理解为“Git 操作触发脚本，脚本再调用仓库命令”。

典型流程如下：

1. 开发者修改代码。
2. 开发者显式暂存本次要提交的文件，例如使用 `git add <path>`。
3. 开发者执行 `git commit`。
4. Git 触发 `.husky/pre-commit`。
5. `pre-commit` 执行仓库约定的检查命令。
6. 如果检查通过，提交继续创建。
7. 如果检查失败，提交被中断，开发者需要修复问题后重新提交。

在这个项目里，主流程的关键不在 `.husky` 文件本身，而在它调用的下游命令。按照现有规则，重点应继续追踪：

- `package.json` 中的 `scripts`，尤其是 `check`、lint、typecheck、生成物检查相关命令。
- 与 lockfile 保护相关的脚本或配置。
- 发布和 shrinkwrap 相关脚本，例如 `scripts/generate-coding-agent-shrinkwrap.mjs`。
- 各 package 下的配置文件，例如 TypeScript、Vitest、lint 或格式化配置。

`.husky` 在这个链路中承担“入口”和“阻断器”的角色：它本身不应包含复杂业务判断，复杂逻辑通常应该放在可复用脚本里，这样本地 hook、CI、发布脚本都能调用同一套检查。

## 推荐阅读顺序

建议按“从入口到被调用命令”的顺序阅读，而不是从业务包开始翻。

第一步，先看 `.husky` 目录下有哪些 hook 文件。重点确认是否存在 `pre-commit`、`commit-msg`、`pre-push`。这里只需要理解每个 hook 什么时候被 Git 调用，不要一开始陷入 shell 细节。

第二步，阅读 `.husky/pre-commit`。目标是找出它调用了哪些命令，例如 `npm run check`、自定义 `node scripts/...`、`npx lint-staged` 或 lockfile 检查脚本。这里要关注失败条件：哪些命令非零退出会阻止提交。

第三步，回到 `package.json`，查看 `.husky` 中出现的 npm script。比如如果 hook 调用了 `npm run check`，就继续沿着 `check` 展开，理解它组合了哪些子检查。

第四步，阅读被 npm script 调用的脚本文件。对于这个仓库，尤其要留意 lockfile、shrinkwrap、models generated、release 相关脚本，因为开发规则明确说明这些文件和流程有特殊提交约束。

第五步，再看 CI 或 release 配置。这样可以判断 `.husky` 的本地检查和远端 CI 是否重复、互补，还是只覆盖开发者本地常见失误。

## 常见误区

第一个误区是把 `.husky` 当成项目质量检查的全部。它只是 Git hook 入口，真正的质量规则通常在 `package.json`、脚本目录和 CI 配置里。阅读 `.husky` 时要顺藤摸瓜，而不是只看 hook 文件本身。

第二个误区是用 `git commit --no-verify` 绕过 hook。当前仓库规则明确禁止这种做法。绕过 hook 会让本地提交跳过 pre-commit 检查，可能把 lockfile、生成物或类型错误带入提交历史。

第三个误区是用 `git add -A` 或 `git add .` 后依赖 hook 兜底。仓库规则要求只暂存本次会话自己修改的明确路径。`.husky` 可以阻止一部分问题，但不能替开发者判断哪些文件属于其他并行会话。

第四个误区是认为 lockfile 变化只要能通过测试就可以提交。当前规则说明 lockfile 变更需要显式允许，提交前会受到 `PI_ALLOW_LOCKFILE_CHANGE=1` 之类环境变量控制。也就是说，这类文件变更被视为需要额外审查的高敏感改动。

第五个误区是直接修改生成文件来通过 hook。例如 `packages/ai/src/models.generated.ts` 这类生成物不应直接改，正确路径是修改生成脚本再重新生成。`.husky` 或 `npm run check` 很可能会暴露这类不一致。

第六个误区是把 Husky hook 当成跨平台业务脚本来写复杂逻辑。Hook 脚本应尽量薄，只负责调用稳定的仓库命令。复杂检查应该沉到 Node 脚本或 npm script 中，便于 CI 和本地复用，也便于排查失败原因。
