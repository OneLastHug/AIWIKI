# 目录：.github

## 它负责什么

`.github` 是这个仓库的协作与自动化中枢，不承载业务代码，主要负责三类事情：入口规范、贡献者门禁、持续集成与发布流程。  
从当前片段看，它把“谁能提 issue / PR”“新请求怎么分流”“主分支怎么验证”“打 tag 后怎么出发布产物”这几条链路都集中在这里维护。仓库根脚本在 `package.json`，而 `.github` 里的工作流负责把这些脚本串成 GitHub Actions 流程。

## 直接子目录地图

- `.github/ISSUE_TEMPLATE`：issue 入口定义区，控制用户在 GitHub 上新建问题时看到的表单。
- `.github/workflows`：自动化流程定义区，包含 CI、发布、门禁、审计等工作流。
- `.github/APPROVED_CONTRIBUTORS`：贡献者白名单与能力标记文件，是多个门禁工作流共同读取的政策源。

## 关键入口

- `.github/ISSUE_TEMPLATE/bug.yml`：Bug 报告表单，面向故障反馈。
- `.github/ISSUE_TEMPLATE/contribution.yml`：贡献提案表单，面向新功能或变更建议。
- `.github/ISSUE_TEMPLATE/config.yml`：issue 入口控制，禁止空白 issue，并把问答导向支持渠道。
- `.github/APPROVED_CONTRIBUTORS`：用户与能力映射，格式是 `<username> <capability>`，其中 capability 目前能看到 `issue` 和 `pr`。
- `.github/workflows/ci.yml`：主干 CI，执行安装、构建、检查、测试。
- `.github/workflows/build-binaries.yml`：发布二进制与 GitHub Release 的入口，通常绑定 tag。
- `.github/workflows/issue-gate.yml`、`.github/workflows/pr-gate.yml`、`.github/workflows/openclaw-gate.yml`、`.github/workflows/approve-contributor.yml`：围绕 issue / PR 的准入和自动处理。
- `.github/workflows/npm-audit.yml`：定期安全审计。

## 主流程位置

1. 贡献入口先落到 `ISSUE_TEMPLATE`。`bug.yml` 和 `contribution.yml` 决定外部提交者最先看到的表单结构，`config.yml` 则限制空白 issue，减少无效流量。  
2. 准入判断集中在 `APPROVED_CONTRIBUTORS`。`issue-gate.yml`、`pr-gate.yml`、`openclaw-gate.yml` 会读取这个文件，并结合 GitHub 权限判断作者是否已被放行。`approve-contributor.yml` 则会根据评论中的 `lgtm` / `lgtmi` 信号更新这份名单。  
3. 主分支验证走 `ci.yml`。它对应仓库根脚本里的 `npm run build`、`npm run check`、`npm test`，也就是说 `.github` 在这里只是编排器，真正的构建逻辑在 `package.json` 和各包脚本里。  
4. 发布流程走 `build-binaries.yml`。它会在 tag 推送时触发，调用 `scripts/build-binaries.sh` 构建产物，再用 `scripts/release-notes.mjs` 生成发布说明，最后创建或更新 GitHub Release。  
5. 安全维护走 `npm-audit.yml`，是独立于主开发流的定时健康检查。

## 推荐阅读顺序

先看 `APPROVED_CONTRIBUTORS`，再看 `ISSUE_TEMPLATE/config.yml`，然后读 `bug.yml` 和 `contribution.yml`，这样能先理解入口策略。  
接着看 `issue-gate.yml`、`pr-gate.yml`、`openclaw-gate.yml`，理解新贡献者为什么会被自动拦截或放行。  
之后看 `ci.yml` 和 `build-binaries.yml`，把主干验证与发布链路串起来。  
最后补 `approve-contributor.yml` 和 `npm-audit.yml`，就能把这个目录的治理闭环补齐。

## 常见误区

- 误以为 `.github` 只是“配置文件夹”。实际上这里决定了仓库的协作政策和自动化边界。  
- 误以为 issue 模板只是文字说明。它同时影响字段结构、默认标签和提交流程。  
- 误以为 `APPROVED_CONTRIBUTORS` 只是记录名单。它是多个工作流共享的准入事实来源。  
- 误把 `build-binaries.yml` 当成普通 CI。它更接近发布流水线，绑定 tag、产物和 Release。  
- 误忽略 `pull_request_target` 的意义。这里的门禁工作流是在目标仓库上下文里运行的，属于敏感入口，代码和权限边界都比普通 `pull_request` 更重要。
