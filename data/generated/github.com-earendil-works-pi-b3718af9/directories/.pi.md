# 目录：.pi

## 它负责什么

`.pi` 是这个仓库的项目级工作目录，主要放“给 pi 运行时加载的本地资源”，而不是业务源码。根据当前片段推断，它承担三类角色：一是项目内的 prompt 模板入口，二是项目内的技能与扩展入口，三是本地缓存/安装占位目录。它和用户级的 `~/.pi/agent` 对应，区别在于这里是跟着仓库走的，适合做项目专属的工作流、提示词和扩展。

从仓库里的文档和代码看，`packages/coding-agent/src/config.ts` 把默认配置目录定为 `.pi`，而 `packages/coding-agent/docs/prompt-templates.md`、`packages/coding-agent/docs/skills.md` 说明了它会被扫描并参与启动时的资源发现。

## 直接子目录地图

- `prompts/`：项目级 slash command 模板目录。这里的每个 `.md` 都对应一个命令入口，适合放高频工作流。
- `extensions/`：项目级扩展代码目录，放运行时注入的 TS 扩展，偏交互增强和会话辅助。
- `skills/`：项目级 skill 目录，放可按需加载的能力包，通常是某个专门任务的完整操作说明。
- `npm/`：本地 npm 安装目录占位。根据当前片段推断，它是项目本地包安装的缓存根之一。
- `git/`：本地 git 安装目录占位。根据当前片段推断，它是项目本地 git 包安装的缓存根之一。

`npm/.gitignore` 和 `git/.gitignore` 都是只保留目录本身、忽略内容的占位文件，说明这两层更像运行时工作区，而不是提交源码。

## 关键入口

如果从目录内部看，最核心的入口是 `prompts/wr.md`。它的描述是“把当前任务端到端做完”，流程里明确包含 changelog、最终评论、commit 和 push，所以它更像项目里的总收口入口。与它并列的专项入口还有：

- `prompts/pr.md`：面向 PR 审查的工作流。
- `prompts/is.md`：面向 issue 分析的工作流。
- `prompts/cl.md`：面向发版前 changelog 审核的工作流。
- `prompts/sa.md`：面向 GitHub security advisory 处理的工作流。

如果从代码层看，真正决定 `.pi` 被识别和加载的入口在 `packages/coding-agent/src/config.ts`，而 prompt/skill 的发现规则则分别在 `packages/coding-agent/docs/prompt-templates.md`、`packages/coding-agent/docs/skills.md` 里说明。

## 主流程位置

主流程不是单个文件，而是“目录资源 + 启动时发现 + 交互时注入”这一条链路。

1. 启动时，`packages/coding-agent/src/config.ts` 通过 `configDir: ".pi"` 这类配置把项目级目录定下来。
2. 随后 pi 扫描 `.pi/prompts/` 和 `.pi/skills/`，把它们变成可用命令或可加载能力。项目级资源通常只在项目被信任后启用。
3. 交互过程中，`.pi/extensions/*.ts` 里的扩展会参与 UI 和会话行为增强。比如：
   - `prompt-url-widget.ts` 会识别 PR / issue / advisory 类型的 prompt，拉取 GitHub 元数据后更新会话标题和侧边 widget。
   - `tps.ts` 会在 agent 结束时根据 assistant 消息 usage 计算吞吐并通知。
   - `redraws.ts` 会注册 `/tui`，用于查看 TUI 重绘统计。
4. 任务执行层面，`prompts/wr.md` 这种模板会把工作流串起来，推动 changelog、评论、提交和推送这些收尾动作。

## 推荐阅读顺序

1. 先看 `packages/coding-agent/docs/prompt-templates.md`，确认 prompt 模板是怎么被发现和命令化的。
2. 再看 `packages/coding-agent/docs/skills.md`，理解 skill 的加载规则和信任边界。
3. 然后看 `.pi/prompts/wr.md`，把这套目录最核心的“收尾工作流”先建立起来。
4. 接着看 `.pi/prompts/pr.md`、`is.md`、`cl.md`、`sa.md`，把专项工作流按用途分开。
5. 最后看 `.pi/extensions/prompt-url-widget.ts`、`tps.ts`、`redraws.ts`，理解这个目录如何影响交互层。

## 常见误区

- 把 `.pi` 当成业务源码目录。它实际更像项目级配置和运行时资源目录。
- 把 `prompts/` 当成普通文档。它们是可执行式工作流入口，会直接驱动 pi 的命令行为。
- 忽略 `skills/` 的信任前提。根据文档，项目级 skill 只有在项目被信任后才会被加载。
- 以为 `npm/`、`git/` 里会有需要手写维护的源码。根据当前片段推断，它们主要是本地安装/缓存占位，不是主要开发资产。
- 只看 `.pi` 目录本身，不回头看 `packages/coding-agent/src/config.ts` 和相关 docs。真正的加载规则在代码和文档里，这个目录只是载体。
