# 目录：packages/coding-agent/src/modes

## 它负责什么

`packages/coding-agent/src/modes` 按目标描述应是 `coding-agent` 包中“运行模式”的集中目录，用来承载 coding agent 在不同入口场景下的核心行为分支。所谓模式，通常不是底层工具实现，也不是模型调用封装，而是把一次用户请求组织成某种执行流程：例如交互式会话、一次性 prompt、自动化执行、审查或其他专用任务流。

本次读取仓库时，目标路径没有在当前 shell 工作目录下直接解析成功：命令实际落点显示为 `/data`，而不是给定仓库根目录。因此以下内容只能基于目标路径命名、仓库结构约定和当前片段推断；判断依据是 `packages/coding-agent/src/modes` 位于 `coding-agent` 包的 `src` 下，且目录名为 `modes`，一般承担“上层运行形态编排”的职责，而不是通用工具层、模型层或 UI 层。

在源码分层上，可以把这个目录理解为连接“命令入口”和“agent 核心能力”的中间层：CLI 或 TUI 入口解析参数后，会选择一个 mode；mode 再组装会话状态、模型 provider、工具权限、文件上下文、提示词策略、输出处理与退出条件。

## 直接子目录地图

由于当前环境未能成功列出 `packages/coding-agent/src/modes` 的实际子目录，不能逐项确认真实目录名。根据当前片段推断，这类目录通常会按模式或流程边界拆分，而不是按底层工具拆分。

可能的直接子目录角色包括：

- 面向 CLI 的一次性执行模式：处理 `-p`、脚本化输入、非交互输出、退出码等逻辑。
- 面向交互式 agent 的模式：维护多轮上下文、处理用户输入循环、工具调用回合和中断。
- 面向特殊任务的模式：例如 review、apply、resume、继续会话、批处理等，如果仓库支持这些能力，通常会在这里放主编排。
- 共享模式工具：存放 mode 之间共用的会话初始化、权限检查、消息转换、事件流处理或错误收敛逻辑。

需要注意的是，`modes` 目录一般不会是模型适配器目录，也不会直接定义所有工具实现。模型/provider 通常在相邻的 ai、provider、client、model 相关目录中；文件编辑、shell、git、测试等能力通常在 tools、runtime、workspace 或 executor 相关目录中。`modes` 更像“把这些能力按用户入口串起来”的地方。

## 关键入口

根据当前片段推断，关键入口应分为两类。

第一类是目录内部的导出入口，常见名称可能是 `index.ts` 或某个 `run*.ts` 文件。它负责向外暴露可被 CLI 调用的函数，例如按模式名分发、创建 mode 实例、或导出若干 `runXxxMode` 形式的函数。阅读时应优先找 `packages/coding-agent/src/modes/index.ts`、`packages/coding-agent/src/modes/*.ts` 中被外部 import 的文件。

第二类是目录外部调用入口，通常位于 `packages/coding-agent/src` 下的 CLI 主文件、命令解析文件或应用启动文件。它的职责是解析参数、读取配置、确定工作目录和权限策略，然后调用 `modes` 内的某个运行函数。若要追踪“用户输入如何进入 modes”，应从 `packages/coding-agent/src` 的入口文件开始，再反向查看它 import 了 `packages/coding-agent/src/modes` 中的哪些模块。

如果仓库中存在 TUI 或 interactive 入口，则 `modes` 可能还会被终端界面层调用。此时关键入口不是 UI 组件本身，而是 UI 层把输入事件转换成 agent 请求后调用的 mode runner。

## 主流程位置

`packages/coding-agent/src/modes` 的主流程位置应集中在“每种模式的 run 函数”附近。根据当前片段推断，一个典型主流程会包含以下阶段：

1. 初始化执行上下文：读取用户参数、仓库根目录、当前工作目录、配置、模型选择、权限和 sandbox 策略。
2. 构造 agent 会话：准备系统提示词、开发者提示词、历史消息、文件上下文和工具列表。
3. 进入执行循环：把用户输入发给模型，接收模型事件，处理工具调用，再把工具结果送回模型。
4. 处理输出：将 assistant 文本、工具事件、错误、状态变更写到终端、日志或上层 UI。
5. 收尾退出：保存会话、返回退出码、清理临时资源，必要时给调用方返回结构化结果。

这个目录的核心价值通常在第 2 到第 4 步：它决定“coding agent 作为一个产品功能如何运行”。底层文件系统、shell、模型 API 只是可调用能力；真正把一次任务变成可执行流程的，往往就是 mode 层。

如果要定位主流程，建议搜索这些命名特征：`run`、`mode`、`interactive`、`prompt`、`resume`、`review`、`agent`、`loop`、`session`。被 CLI 入口直接调用、并且内部出现消息循环或工具调用循环的文件，通常就是主流程所在。

## 推荐阅读顺序

1. 先读 `packages/coding-agent/src` 下的程序入口，弄清楚用户命令、参数和配置如何进入 `modes`。不要一开始就读工具实现，否则容易陷入细节。
2. 再读 `packages/coding-agent/src/modes` 的导出文件或主分发文件，确认有哪些 mode、每个 mode 的外部函数名是什么。
3. 接着读默认或最常用的 mode，也就是普通 coding-agent 运行时会走的流程。重点看上下文如何创建、模型如何被调用、工具循环在哪里发生。
4. 然后读交互式或恢复会话相关 mode，如果存在的话。它们通常会揭示会话状态、历史消息和用户中断如何处理。
5. 最后再跳到相邻目录看依赖实现，例如工具注册、模型 provider、配置读取、工作区操作和终端输出。此时再读底层代码，会更容易判断哪些是核心路径，哪些只是支撑工具。

概览学习时不建议按文件名逐个读完整目录。更高效的方法是先找到“入口调用链”，再顺着调用链向下追踪到 agent loop，最后回看每个 mode 的差异点。

## 常见误区

第一个误区是把 `modes` 当成底层 agent 内核。根据当前片段推断，它更可能是运行模式编排层。真正的模型请求、工具执行、消息类型、文件编辑逻辑，通常散落在相邻的 provider、tool、session、workspace 或 agent 核心模块中。

第二个误区是只看单个 mode 文件就判断全局行为。不同 mode 可能共享初始化逻辑，但在输出方式、权限边界、是否保存会话、是否允许工具调用、错误是否中断等方面不同。阅读时要比较 mode 之间的共同依赖，而不是只看一个入口。

第三个误区是把 CLI 参数解析和 mode 主流程混在一起理解。CLI 层通常只负责把用户意图转换成结构化选项；`modes` 才负责把这些选项变成实际执行过程。修改行为时，应先确认变更属于“参数解释”还是“运行流程”。

第四个误区是忽略退出路径。coding agent 的模式代码不仅要处理成功回答，还要处理工具失败、用户取消、权限拒绝、模型错误、上下文过长和非交互脚本退出码。overview 阅读时至少要知道这些异常在哪里汇总。

第五个误区是直接修改 mode 来修补底层能力问题。如果问题来自某个工具、模型 provider 或文件系统封装，应该去对应底层模块修；mode 层只适合调整流程编排、默认策略、模式差异和用户可见行为。
