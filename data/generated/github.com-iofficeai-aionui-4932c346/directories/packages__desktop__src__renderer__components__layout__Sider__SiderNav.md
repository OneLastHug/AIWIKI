# 目录：`packages/desktop/src/renderer/components/layout/Sider/SiderNav`

## 它负责什么

根据当前片段推断，这一层是桌面端主布局里“侧边导航”的渲染入口，职责更偏 UI 组织而不是业务处理。它通常负责把导航项、分组、当前选中态、折叠态、图标和路由跳转关系拼成一个可复用的侧栏模块，并把上层 layout 传下来的状态展示出来。

结合仓库里可见的同类结构，侧边栏相关逻辑通常不会散落在页面层，而是集中在 layout 体系中，由更上层的 `Sidebar` 或 `Sider` 入口统一驱动。也就是说，这个目录更像“侧栏导航组件的落点”，而不是功能页本身。

## 直接子目录地图

由于当前检查到的仓库片段里没有直接命中这个精确目录名，下面按项目中同类侧栏模块的组织方式做推断，依据是 `src/routes/(main)/*/_layout/Sidebar` 这一组目录的拆法。常见的直接子目录会围绕“展示层、状态层、数据整理层”分开：

- `Header`：侧栏顶部区域，通常放标题、切换入口、搜索或快捷按钮。
- `Body` 或 `Content`：侧栏主体，承载导航列表、分组列表、当前页面入口。
- `NavItem`、`Item`、`List`：单个导航项与列表容器，负责选中、悬停、徽标、图标等细节。
- `hooks`：处理折叠、选中同步、展开收起、路由联动等状态逻辑。
- `utils`：整理导航数据、过滤可见项、做排序或分组映射。
- `types` / `constants`：放类型定义和静态配置，避免在组件里硬编码。

如果这个目录比普通侧栏更细，通常还会出现 `Menu`、`Group`、`Drawer` 之类的小子目录，但从当前证据看，不能确认它一定存在。

## 关键入口

就目录角色而言，真正的入口一般不是“叶子组件”，而是被上层 layout 引用的组合组件。当前仓库里最接近的主入口位置，出现在这些 layout 侧栏目录中：

- `src/routes/(main)/agent/_layout/Sidebar`
- `src/routes/(main)/group/_layout/Sidebar`
- `src/routes/(main)/community/_layout/Sidebar`
- `src/routes/(main)/eval/_layout/Sidebar`

这些目录说明：侧边栏在项目里是按“场景路由”挂载的，而不是一个全局单例。`SiderNav` 如果存在，大概率就是被这些 layout 侧的容器组件再包一层后使用，负责具体导航展示。

## 主流程位置

主流程一般是“上层 layout 计算状态 -> 传入侧栏容器 -> 侧栏容器拆分成导航区域 -> 具体导航项渲染与路由切换”。

从当前片段能看到的最核心流程位置，集中在以下几类目录：

- `src/routes/(main)/*/_layout/Sidebar`：侧栏主容器，承接页面状态和布局控制。
- `src/routes/(main)/*/_layout/Sidebar/Header`：顶部控制区，通常先于导航列表渲染。
- `src/routes/(main)/*/_layout/Sidebar/Topic`、`.../List`、`.../Item`：导航数据到列表项的逐级拆分。
- `src/routes/(main)/_layout/DesktopLayoutContainer`：更上层的桌面布局壳，决定侧栏是否显示、宽度、折叠策略等。

如果 `SiderNav` 在 renderer 组件层承担导航渲染，那么它的主流程就是“接收结构化菜单数据 -> 计算高亮/展开态 -> 逐项渲染 -> 响应点击并触发路由或状态切换”。

## 推荐阅读顺序

1. 先看上层布局容器，理解侧栏何时出现、宽度怎么定、状态从哪里来。
2. 再看同类 `Sidebar` 目录，确认侧栏数据是怎么分层的。
3. 然后看 `Header` 和 `List`、`Item` 这类子块，抓住导航展示的主路径。
4. 最后回到 `SiderNav` 目录本身，核对它到底是纯展示、带状态，还是兼有数据整理。

## 常见误区

- 把 `SiderNav` 当成页面级业务模块。它更像布局组件的一部分，重点是导航组织，不是业务流程编排。
- 认为它会直接处理数据拉取。按项目分层习惯，数据获取通常在更上层或独立状态层完成，这里更多是消费数据。
- 忽略路由层入口。这个目录的真实调用点通常在 `src/routes/(main)/*/_layout/Sidebar` 一类文件夹里，而不是孤立存在。
- 把“目录名”当成“固定实现”。根据当前片段推断，这类侧栏目录在不同场景下会复用相似拆法，但具体子目录是否齐全，要以实际源码为准。
