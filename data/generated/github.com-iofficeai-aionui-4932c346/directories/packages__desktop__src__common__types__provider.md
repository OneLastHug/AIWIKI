# 子系统：packages/desktop/src/common/types/provider

## 解决什么问题

这个目录存放的是“provider 相关的公共类型层”。从目录名和文件名看，它的职责不是实现业务逻辑，而是把各类 provider 的数据结构先统一定义好，让 `process`、`renderer`、`preload` 以及共享工具都能用同一套类型沟通。

根据当前片段推断，它主要解决两类问题：一是 provider 接口调用时的入参、出参、错误信息如何表示；二是语音类 provider 的配置、能力描述、返回结果如何标准化。这样做的价值是避免不同模块各写一套字段名，减少跨进程传参时的歧义。

## 相关目录和文件

当前目录下可见两个核心文件：

- `packages/desktop/src/common/types/provider/providerApi.ts`：provider API 的通用类型定义，通常会覆盖请求参数、返回数据、状态枚举或错误结构。
- `packages/desktop/src/common/types/provider/speech.ts`：语音 provider 相关类型，通常会描述语音合成、识别、音色、语言、采样参数等字段。

它们所在的 `common/types` 层，通常会被更上层的业务目录复用，而不是反过来依赖业务实现。也就是说，这里是“类型契约”而不是“功能代码”。

## 核心对象

根据命名可以把这里的核心对象理解为两组：

- `providerApi` 相关对象：面向所有 provider 的通用 API 契约，比如 provider 标识、调用参数、结果包裹结构、错误码或能力声明。
- `speech` 相关对象：面向语音能力的专用契约，比如语音合成任务、语音识别结果、声音配置、语言/口音配置等。

如果项目里还有其他 provider 模块，通常也会沿着同样风格继续扩展，但目前目录中只看到这两个文件，所以更像是一个“通用 provider 基础类型 + 语音专项类型”的小型子系统。

## 运行流程

这里没有运行时逻辑，更多是数据流上的“约束层”。典型流程是：

1. 上层页面或服务构造 provider 请求。
2. 请求对象先按 `providerApi.ts`、`speech.ts` 中定义的类型组装。
3. 通过 IPC 或共享服务传到 `process` 层执行真正的 provider 访问。
4. `process` 层返回结果后，再按同一套类型回传给 `renderer` 展示。
5. 如果字段不一致，TypeScript 会在编译期直接暴露问题。

所以这个目录本身不负责“做事”，它负责让“各层说同一种语言”。

## 上下游依赖

上游依赖通常来自业务调用方，包括设置页、模型/能力管理页、provider 适配器、以及真正执行外部 API 请求的服务层。下游依赖则是更底层的 provider 实现、IPC 消息格式、以及渲染层的表单和状态展示组件。

从架构上看，这类类型文件一般应当保持纯净，不依赖 DOM、Node.js 或具体第三方 SDK。它们最好只依赖 TypeScript 基础类型，以及项目内部更基础的常量或通用类型。

## 修改时最容易踩的坑

最常见的坑是“只改一个地方，其他地方没同步”。provider 类型一旦变动，`process` 里的实现、`renderer` 里的表单、测试用例、以及可能的 mock 数据都可能一起受影响。

第二个坑是字段语义混乱。比如语音相关字段里，哪些是 provider 配置，哪些是一次调用参数，哪些是返回结果，最好分开定义，不要把一个类型写得过于宽泛。

第三个坑是破坏跨进程契约。这里属于 `common` 层，任何变更都可能影响多个进程边界，尤其要避免把运行时专属对象直接塞进公共类型里。根据当前片段推断，这也是为什么目录单独拆成 `provider` 子目录，而不是散落在别处。

## 推荐阅读顺序

1. 先看 `providerApi.ts`，建立 provider 通用契约的整体认识。
2. 再看 `speech.ts`，理解语音能力是如何在通用契约之上做专门化的。
3. 接着回到调用方，查看 `packages/desktop/src/process/` 里真正使用这些类型的 provider 实现。
4. 最后看 `packages/desktop/src/renderer/` 中对应的设置页或表单，确认这些类型如何映射到用户界面和交互流程。
