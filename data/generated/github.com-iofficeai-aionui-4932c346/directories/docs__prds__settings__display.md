# 目录：docs/prds/settings/display

## 它负责什么

`docs/prds/settings/display` 按路径命名应属于产品需求文档区 `docs/prds` 下的“设置 / 显示”专题，用来承载 Display Settings 相关的 PRD、交互说明、状态约束、验收口径或后续拆分设计。它不是运行时代码目录，而是面向产品、设计、前端实现和测试对齐的文档目录。

但根据当前可读取片段，目标目录本身未能被确认存在：读取 `docs/prds/settings/display`、`docs/prds/settings` 时均返回不存在；进一步定位只能确认仓库中存在 `docs/prds` 这一上层目录，未确认到 `settings/display`。因此下面的说明以“路径角色”和“根据当前片段推断”为主，不把不存在的文件当作事实展开。

从命名看，`settings/display` 的职责边界应聚焦在“显示偏好”而非通用设置。例如主题模式、界面缩放、字体大小、语言之外的视觉展示偏好、侧边栏显示方式、窗口或布局密度等，都可能属于这一类；账户、安全、模型、快捷键、通知、存储等内容则不应放到这个目录下，除非它们直接影响显示体验。

## 推荐阅读顺序

建议先从 `docs/prds` 的目录结构读起，确认 PRD 文档的整体组织方式和命名习惯。当前片段只能确认这一层存在，因此这是最稳妥的起点。

第二步阅读 `docs/prds/settings`，如果该目录存在，应先理解 Settings 模块的范围划分：哪些配置归入设置页，设置页是否按 General、Display、Model、Account 等分区组织，是否有统一的导航、保存、重置、校验和持久化规则。

第三步再进入 `docs/prds/settings/display`。如果有 `README.md` 或 `index.md`，先读总览；没有总览时，按“主题 / 布局 / 字体或缩放 / 其他显示偏好”的顺序读功能文档。这样能先建立显示设置的整体模型，再看单项规则。

第四步才建议跳到实现代码或测试。显示设置通常会影响 renderer 层 UI、主题变量、UnoCSS 或 Arco 主题覆盖、i18n 文案和配置持久化。没有先读 PRD 就直接看代码，容易把实现现状误认为产品目标。

## 常见误区

第一个误区是把 `docs/prds/settings/display` 当成源码目录。按路径看，它属于 PRD 文档，不应期待这里出现组件、hook、store 或 IPC 实现。这里的价值在于定义需求边界、用户流程和验收口径。

第二个误区是把“显示设置”等同于“主题设置”。主题只是显示设置的一部分；字体、缩放、布局密度、内容展示偏好、跟随系统等都可能属于 Display 范畴。反过来，语言切换、账号偏好、模型配置虽然会出现在设置页，但不一定属于 display。

第三个误区是忽略上层 `settings` 的统一规则。显示设置通常要服从设置页整体的信息架构、保存策略、重置策略和错误处理。如果只看 display 单目录，可能遗漏跨设置项的公共流程。

第四个误区是把当前不存在的目录内容当成已实现事实。当前可读证据只确认 `docs/prds` 存在，未确认 `docs/prds/settings/display` 存在。因此对该目录的说明只能作为路径意图和阅读方法，不能替代真实 PRD 内容。

第五个误区是读 PRD 时只关注配置项列表，不关注状态传播。显示类设置的关键往往在“改完之后哪里变化”：当前窗口、所有窗口、下次启动、系统主题变化时是否同步，以及配置冲突时谁优先。这些才是后续实现和测试最容易出问题的位置。
