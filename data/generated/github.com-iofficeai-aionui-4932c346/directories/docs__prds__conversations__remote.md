# 目录：docs/prds/conversations/remote

## 它负责什么

`docs/prds/conversations/remote` 从路径命名看，应该是“远程会话”相关的产品需求文档目录，位于 `docs/prds/conversations` 这一组会话类 PRD 之下。它的职责不是承载运行时代码，而是描述远程 conversation 能力的产品边界、交互流程、状态约束、数据同步关系以及与本地会话能力的差异。

不过，根据当前可读片段，仓库中未能定位到 `docs/prds/conversations/remote`，相邻的 `docs/prds/conversations` 也未能在当前执行上下文下被读取到。因此以下目录角色说明只能基于目标路径语义推断，不能当作对实际文件内容的逐项确认。可靠结论只有两点：一是目标被声明为 PRD 文档目录；二是它被归入 conversations 域下的 remote 子域，说明它关注的不是通用文档，也不是 renderer/process 代码实现，而是远程会话这一产品能力的需求层说明。

在 AionUi 这样的桌面应用结构里，远程会话通常会牵涉用户登录态、云端会话列表、会话详情拉取、消息发送、消息同步、异常重试、离线/在线切换、以及本地缓存和远端数据的一致性策略。若该目录存在，阅读它的目的应是先理解“产品希望远程会话如何工作”，再回到代码中寻找 IPC、renderer 页面、process 服务和数据存储的实现对应关系。

## 直接子目录地图

根据当前片段无法确认 `docs/prds/conversations/remote` 下实际有哪些直接子目录。若目录存在，建议把它理解为 `conversations` 产品域内的一个子模块，而不是独立系统。其可能的子目录组织通常会围绕以下几类材料展开：

`overview` 或 `README` 类入口：用于解释远程会话能力的背景、范围、非目标和术语。

`flows` 类目录：用于描述关键用户路径，例如创建远程会话、打开历史远程会话、发送消息、同步消息状态、处理失败重试。

`states` 或 `sync` 类目录：用于定义本地与远端之间的状态机、同步时机、冲突处理和缓存策略。

`api` 或 `contracts` 类目录：用于说明前后端、桌面端与服务端之间的数据契约。这里如果只是 PRD，通常不会给出完整实现代码，但会定义字段、状态和错误码。

`edge-cases` 或 `errors` 类目录：用于补充网络失败、鉴权过期、会话不存在、消息发送失败、重复消息、跨设备更新等边界场景。

以上是根据当前片段推断，依据是目录名 `docs/prds/conversations/remote` 所表达的领域层级：`docs/prds` 表示产品需求文档，`conversations` 表示会话域，`remote` 表示远程能力分支。

## 关键入口

如果目标目录实际存在，优先寻找的关键入口应是 `docs/prds/conversations/remote/README.md`、`docs/prds/conversations/remote/index.md` 或带有 `overview`、`background`、`requirements` 命名的文档。这类文件通常会回答三个问题：为什么需要 remote conversations、它覆盖哪些用户场景、它和本地 conversations 的边界在哪里。

其次应关注与流程命名相关的文档，例如包含 `flow`、`sync`、`message`、`session`、`conversation` 的文件。这些文件通常是从产品需求映射到实现的桥梁：它们不会直接告诉你代码函数在哪里，但会定义“打开远程会话时先加载什么”“发送消息后 UI 如何变化”“远端更新如何合并到本地视图”等行为。

再次是契约类入口。如果目录中存在 `api`、`schema`、`contract`、`model` 等命名，要把它们视为后续代码检索的锚点。远程会话能力一般会在 renderer 层展示列表和消息，在 process 或 service 层处理请求、持久化与同步，再通过 preload 暴露 IPC 桥接能力。PRD 中的字段名、状态名和错误场景，往往能帮助定位真实实现中的类型定义、store、hook、service 和 IPC channel。

## 主流程位置

根据路径语义推断，主流程应围绕“远程会话生命周期”展开，而不是围绕单个 UI 组件。地图式阅读时，可以把主流程拆成五段。

第一段是会话发现：用户进入 conversations 区域后，系统如何判断是否展示远程会话、如何拉取远端列表、列表排序和筛选规则是什么。

第二段是会话打开：点击某个远程会话后，如何加载元信息、历史消息、分页数据和当前上下文；如果远端不可达，是否使用本地缓存或显示错误态。

第三段是消息交互：用户发送消息后，本地 UI 是否立即插入 pending 消息，远端确认后如何更新状态，失败时是否允许重试或编辑。

第四段是同步更新：远端会话在其他设备或服务端发生变化时，本端如何感知、合并、刷新或提示冲突。这里通常是 remote conversations 最容易出问题的主流程位置。

第五段是异常与恢复：登录失效、网络中断、接口错误、会话被删除、消息重复、顺序错乱等情况如何处理。PRD 若完整，应该在这一部分给出明确产品决策。

## 推荐阅读顺序

建议先读目标目录下的总览文档，例如 `README.md`、`index.md` 或 `overview.md`，先建立术语和范围。不要一开始就跳到 API 或边界场景，否则容易把“技术补丁”误认为“产品主线”。

第二步阅读用户流程或主路径文档，重点找动词：进入、创建、打开、发送、同步、删除、恢复。这些动词会构成远程会话功能的骨架。

第三步阅读状态和数据契约文档，关注 conversation、message、sync status、error status、timestamp、remote id、local id 这类字段和状态。它们通常决定后续代码中的类型、store 和 IPC 接口。

第四步再看异常场景。异常文档应放在主流程之后理解，因为很多异常处理依赖前面定义的正常状态机。

最后再回到仓库实现层检索对应代码。可以从 `packages/desktop/src/renderer` 查 UI 和 hooks，从 `packages/desktop/src/process` 查服务逻辑，从 `packages/desktop/src/preload` 查 IPC 暴露点。具体路径需要结合实际 PRD 文件中的关键词再定位。

## 常见误区

第一个误区是把 `docs/prds/conversations/remote` 当成实现目录。它位于 `docs/prds` 下，核心价值是说明产品需求和行为约束，不应期待在这里找到完整 TypeScript 实现。

第二个误区是只看 remote，不看 conversations 的上层约定。远程会话通常继承通用 conversation 的概念，例如会话标题、消息列表、输入区、历史记录、删除归档等。remote 文档更可能描述增量差异，例如云端同步、鉴权、跨端一致性，而不是重新定义整个会话系统。

第三个误区是把接口字段当成最终代码事实。PRD 中的字段和状态可能是产品层表达，真正实现可能经过命名转换、拆分或合并。阅读时应把它们作为检索线索，而不是直接假设代码中存在同名函数或同名类型。

第四个误区是忽略异常流程。remote conversations 的复杂度主要来自网络、同步和一致性，而不是普通消息列表渲染。只读 happy path 会低估实现风险。

第五个误区是过度逐文件阅读。当前任务是 overview 深度，目标应是建立目录地图和主流程位置。若后续要深入，再按“总览、流程、契约、异常、实现映射”的顺序展开。
