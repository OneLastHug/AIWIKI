# 目录：.github

## 它负责什么

`.github` 是这个仓库的 GitHub 平台配置目录，主要管理“项目协作入口”和“仓库自动化入口”，不承载业务运行代码。它的作用可以分成四类：贡献者规范、Issue/PR 提交流程、依赖更新配置、GitHub Actions 自动化。

从当前片段看，这个仓库本体是一个多组件项目：前端或 Web 应用位于 `next`，Python 平台服务位于 `platform`，命令行工具位于 `cli`，并且还有 `docker-compose.yml`、`db/Dockerfile`、`next/Dockerfile`、`platform/Dockerfile` 等部署或本地运行相关文件。`.github` 目录中的工作流正是围绕这些组件设置自动检查，例如 `next` 变更触发 Node.js CI，`platform` 变更触发 Python 测试平台 CI，`cli`、`next`、`platform` 的依赖则交给 Dependabot 周期性检查。

因此，阅读 `.github` 时不要把它当作应用代码目录，而应把它看作“仓库治理层”：它规定外部贡献者如何提 issue、如何提 PR、提交后哪些检查会跑、哪些依赖会自动更新、主分支推送后是否会触发部署 webhook 或赞助者信息更新。

## 直接子目录地图

`.github/ISSUE_TEMPLATE` 是 Issue 表单模板目录。它包含 bug、功能请求、文档改进三类结构化模板，以及 `config.yml` 这样的 Issue 入口配置。这里决定用户在 GitHub 上点击 New issue 时看到哪些表单、默认标签是什么、哪些字段必须填写，以及是否展示提问或社区讨论入口。需要注意：模板里存在外部社区链接，文档中只需知道它们用于引导问答和讨论，不需要依赖具体地址。

`.github/PULL_REQUEST_TEMPLATE` 是 PR 模板目录。当前核心文件是 `pull_request_template.md`，它定义 PR 描述结构，包括变更说明、动机、测试方式、截图、变更类型、检查清单和条款确认。它的角色是约束贡献者在提交代码前说明“改了什么、为什么改、怎么测”。

`.github/workflows` 是 GitHub Actions 工作流目录，是自动化主入口。当前包含 `node.js.yml`、`python.yml`、`sponsors.yml`、`webhooks.yml`。其中前两个面向代码质量和测试，后两个面向维护流程和部署触发。

根层级文件还包括 `CODE_OF_CONDUCT.md`、`CONTRIBUTING.md`、`SECURITY.md`、`SUPPORT.md`、`FUNDING.yml`、`dependabot.yml`。这些不是子目录，但在 `.github` 的职责里很关键：它们分别对应社区行为准则、贡献说明、安全披露、支持说明、赞助配置和依赖更新策略。

## 关键入口

最重要的自动化入口是 `.github/workflows/node.js.yml`。它的名称是 `Node.js CI`，在 `main` 分支 push 或 pull request 时触发，但只关注 `next/**` 路径。工作目录固定为 `next`，使用 Node.js 18，执行 `npm ci`、`npm test`，并在测试时提供占位的 `OPENAI_API_KEY`。最后还会运行 `./prisma/useSqlite.sh && npm run postinstall`，说明 `next` 组件的测试或生成流程和 Prisma、SQLite 本地化配置有关。

第二个关键入口是 `.github/workflows/python.yml`。它的名称是 `Testing Platform`，只在 pull request 到 `main` 且路径匹配 `platform/**` 时触发。它使用 Python 3.11 和 Poetry，分成 `black`、`mypy`、`pytest` 三个 job。`black` 检查格式，`mypy` 检查类型，`pytest` 运行测试并启用覆盖率。`pytest` job 还启动 MySQL 8 服务，设置 `REWORKD_PLATFORM_DB_HOST`、`REWORKD_PLATFORM_KAFKA_BOOTSTRAP_SERVERS` 等环境变量。根据当前片段推断，`platform` 是后端或平台服务层，测试需要数据库依赖，Kafka 相关配置可能被应用配置读取，但工作流里没有真正启动 Kafka 服务。

`.github/dependabot.yml` 是依赖维护入口。它配置每周检查三个生态：`/cli` 的 npm、`/next` 的 npm、`/platform` 的 pip。这里揭示了仓库的主要语言和包管理边界：`cli` 与 `next` 走 JavaScript/Node 生态，`platform` 走 Python 生态。

`.github/workflows/webhooks.yml` 是部署触发入口。它在手动触发或 `main` 分支 push 时运行，但通过 `if: github.repository == 'reworkd/AgentGPT'` 限定只在原始仓库中执行。它使用 production environment，并通过 secrets 调用部署 webhook。文档阅读时应理解为“主仓库主分支合并后的外部部署通知”，而不是本地部署脚本。

`.github/workflows/sponsors.yml` 是维护性自动化入口。它支持手动触发和每日定时触发，用 action 更新 `README.md` 中的赞助者信息，并创建自动 PR。它不影响构建测试主链路，但会改变仓库文档类内容。

## 主流程位置

贡献协作主流程从 `.github/ISSUE_TEMPLATE` 和 `.github/PULL_REQUEST_TEMPLATE` 开始。用户或贡献者先通过 Issue 模板提交 bug、feature 或 docs 反馈；开发者实现后通过 PR 模板说明变更、动机、测试和类型；合并前 GitHub Actions 根据变更路径触发不同检查。

前端相关主流程位于 `.github/workflows/node.js.yml`，路径过滤是 `next/**`。也就是说，只有 `next` 目录下的文件变化才会触发这条 Node.js CI。它不覆盖 `cli`，虽然 `cli` 也被 Dependabot 管理。

平台服务相关主流程位于 `.github/workflows/python.yml`，路径过滤是 `platform/**`。这里的主流程更完整：格式、类型、单测分别拆成独立 job，失败点更容易定位。由于 `pytest` job 启动 MySQL 服务，涉及数据库访问的测试应优先对照这里的环境变量和服务名。

依赖升级主流程位于 `.github/dependabot.yml`。它不是 CI 检查，而是生成依赖更新 PR 的配置。根据当前片段推断，Dependabot 生成的 PR 仍会根据其改动路径触发对应工作流，例如 `next` 依赖更新触发 Node.js CI，`platform` 依赖更新触发 Python CI。

部署或外部系统通知主流程位于 `.github/workflows/webhooks.yml`。它和测试不同，不依赖路径过滤，而是监听 `main` 分支 push 与手动触发，并且依赖 GitHub secrets。普通 fork 或本地环境通常不会执行这条生产 webhook。

## 推荐阅读顺序

建议先读 `.github/workflows/node.js.yml` 和 `.github/workflows/python.yml`，因为它们直接告诉你这个仓库最关心哪些组件、每个组件的验证命令是什么、CI 的触发边界在哪里。理解这两个文件后，再回到仓库根目录的 `next/package.json`、`platform/pyproject.toml` 去对应实际脚本和依赖，会更容易建立项目结构感。

第二步读 `.github/dependabot.yml`，用它确认包管理边界：`cli`、`next`、`platform` 是三个独立依赖维护单元。这个文件也能帮助判断“为什么某些目录有自动依赖 PR，而另一些目录没有”。

第三步读 `.github/PULL_REQUEST_TEMPLATE/pull_request_template.md`。它能反映维护者希望贡献者提供哪些信息，尤其是测试说明、变更类型、用户可见影响和基础 checklist。对于学习仓库协作规范，这比直接读长篇说明更快。

第四步再看 `.github/ISSUE_TEMPLATE`。其中 `bug-report.yaml`、`feature-request.yaml`、`docs.yml` 分别对应缺陷、需求和文档反馈。它们不影响代码执行，但能反映项目维护者如何收集复现步骤、预期行为、替代方案和文档改进建议。

最后阅读 `.github/CONTRIBUTING.md`、`.github/CODE_OF_CONDUCT.md`、`.github/SECURITY.md`、`.github/SUPPORT.md`。这些文件属于社区和安全治理材料，适合在准备真实贡献、报告漏洞或寻求支持时再深入。

## 常见误区

第一个误区是把 `.github/workflows` 当作完整构建说明。这里确实记录了 CI 命令，但它只覆盖特定路径和自动化场景；本地开发还需要结合 `next/package.json`、`platform/pyproject.toml`、`docker-compose.yml` 等文件判断。比如 Node.js CI 使用 SQLite/Prisma 相关脚本，并不代表生产环境一定使用 SQLite。

第二个误区是认为所有组件都有测试工作流。当前片段里 `next` 有 Node.js CI，`platform` 有 Python CI，但 `cli` 只出现在 Dependabot 配置中，没有看到单独的 `cli` CI 工作流。根据当前片段推断，`cli` 的依赖会被自动检查，但代码测试是否由其他路径覆盖，不能仅凭 `.github` 下的文件确认。

第三个误区是忽略路径过滤。`node.js.yml` 只监听 `next/**`，`python.yml` 只监听 `platform/**`。如果一次 PR 只改文档、GitHub 模板或其他目录，未必会触发这些组件测试。判断 PR 检查是否应该运行时，要先看 `on.paths`，而不是只看 workflow 名称。

第四个误区是把 `webhooks.yml` 理解为通用部署脚本。它依赖 secrets、production environment，并且限定仓库名为 `reworkd/AgentGPT`。在 fork、镜像仓库或本地学习场景中，它更多是说明“主仓库合并后会通知外部部署系统”，不是可以直接复用的部署命令。

第五个误区是把 Issue/PR 模板里的外部入口当作源码依赖。这些模板只是 GitHub 协作界面的内容配置，里面的社区、文档或讨论入口不会参与应用构建，也不会影响运行时行为。对于源码学习，重点应放在它们如何塑造协作流程，而不是追踪每一个外部地址。
