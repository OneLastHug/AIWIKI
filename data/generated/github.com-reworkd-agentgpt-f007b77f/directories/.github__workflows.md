# 目录：.github/workflows

## 它负责什么

`.github/workflows` 是本仓库的 GitHub Actions 自动化入口目录，负责把代码变更、质量检查、文档维护和部署触发串起来。它不承载业务代码，而是描述“在什么事件发生时，GitHub 应该启动哪些自动任务”。从当前片段看，这个仓库是多子项目结构：前端或 Next.js 应用在 `next`，Python 平台服务在 `platform`，另有 `cli`、`db`、`docs`、`scripts` 等目录。因此这里的 workflow 也按项目边界拆分，而不是在根目录统一执行一个大流水线。

这个目录下目前没有更深层子目录，只有四个顶层 workflow 文件：`node.js.yml`、`python.yml`、`sponsors.yml`、`webhooks.yml`。它们分别覆盖 `next` 的 Node.js CI、`platform` 的 Python 测试与静态检查、README 赞助者信息自动更新，以及主分支部署 webhook 触发。整体上，这是一个轻量但清晰的自动化层：代码质量检查集中在 Pull Request 或指定路径变更时触发，生产部署触发则绑定 `main` 分支和仓库身份校验。

## 直接子目录地图

`.github/workflows` 当前没有直接子目录。它本身就是 GitHub Actions 的约定目录，GitHub 会扫描该目录下的 `.yml` 或 `.yaml` 文件，并把每个文件注册为一个独立 workflow。

可以把这个目录理解为仓库自动化地图的“扁平索引”：

` .github/workflows/node.js.yml` 面向 `next/**` 的 Node.js CI，运行目录固定到 `next`。

`.github/workflows/python.yml` 面向 `platform/**` 的 Python 检查与测试，运行目录固定到 `platform`。

`.github/workflows/sponsors.yml` 面向仓库 README 的赞助者内容生成，不与业务代码目录绑定。

`.github/workflows/webhooks.yml` 面向生产部署触发，在 `main` 推送或手动触发时调用外部部署 webhook。

## 关键入口

最核心的入口是各 workflow 文件顶部的 `on` 配置。它决定了自动化是否会启动，也决定了变更影响范围。

`node.js.yml` 的入口是 `push` 和 `pull_request`，目标分支为 `main`，并且通过 `paths: next/**` 限制只有 `next` 目录变更才触发。该 workflow 使用 Node.js 18，工作目录是 `next`，依次执行 `npm ci`、`npm test`，然后运行 `./prisma/useSqlite.sh && npm run postinstall`。这说明 `next` 子项目的测试或构建后置步骤依赖 Prisma，并且 CI 中会切到 SQLite 相关配置。根据当前片段推断，`next/prisma` 是理解前端应用数据库生成或客户端生成流程的重要邻近位置，依据是 workflow 明确调用了 `next/prisma/useSqlite.sh`。

`python.yml` 的入口是 `pull_request` 到 `main`，且只关注 `platform/**`。它定义了 `PYTHON_VERSION: "3.11"`，并拆成 `black`、`mypy`、`pytest` 三个 job。三个 job 都在 `platform` 下运行，都先安装 Poetry，再用 `actions/setup-python` 配置 Python 3.11 和 Poetry 缓存，之后 `poetry install`。这表示 `platform/pyproject.toml` 和 `platform/poetry.lock` 是 Python 服务依赖、测试、格式化、类型检查的真实配置入口。

`sponsors.yml` 的入口是 `workflow_dispatch` 和每天一次的 `schedule`。它使用 GitHub Sponsors README action 更新根目录 `README.md`，再通过 `peter-evans/create-pull-request` 创建分支 `workflow/sponsors` 的自动 PR。这里的关键不在源码构建，而在仓库文档维护和赞助者展示自动化。它依赖 `SPONSOR_WORKFLOW_PAT` 这类 secret。

`webhooks.yml` 的入口是 `workflow_dispatch` 和推送到 `main`。它的 job 绑定 `environment: production`，并且有条件 `github.repository == 'reworkd/AgentGPT'`。这说明该部署触发只应在上游正式仓库生效，fork 或镜像环境中即便 workflow 存在，也不会实际调用部署 webhook。外部部署地址和鉴权头来自 secrets，文档中不应展开真实地址。

## 主流程位置

Node.js 主流程位置在 `node.js.yml` 的 `jobs.build.steps`。它是单 job 线性流程：checkout 仓库，安装 Node.js 18，按 `next/package-lock.json` 做 npm 缓存，进入 `next` 执行依赖安装、测试和 Prisma postinstall。学习时应把它与 `next/package.json`、`next/__tests__`、`next/prisma`、`next/src` 一起看，因为 workflow 只是调用层，真实脚本和测试定义在 `next` 子项目内。

Python 主流程位置在 `python.yml` 的三个并列 job：`black`、`mypy`、`pytest`。其中 `black` 负责格式检查，`mypy` 负责类型检查，`pytest` 负责测试覆盖率。`pytest` job 还启动了一个 MySQL 8 服务容器 `reworkd_platform-db`，暴露 `3306`，并注入 `REWORKD_PLATFORM_DB_HOST`、`REWORKD_PLATFORM_KAFKA_BOOTSTRAP_SERVERS` 等环境变量。根据当前片段推断，`platform` 服务测试会触达数据库配置，Kafka 在测试环境中可能被配置为本地地址或由测试替身处理；依据是 workflow 只声明了 MySQL service，没有声明 Kafka service，却传入了 Kafka bootstrap servers。

赞助者更新主流程在 `sponsors.yml` 的 `jobs.deploy.steps`。它先 checkout，再更新 `README.md`，最后创建自动 PR。这条流程对业务运行无影响，但会改变根 README 的内容。

部署触发主流程在 `webhooks.yml` 的 `jobs.invoke.steps`。它没有构建步骤，只用 `curl` 向 secret 中配置的部署 webhook POST `{"ref":"main"}`。因此它更像“通知外部部署系统”的桥，而不是本仓库内完成镜像构建或发布的流水线。

## 推荐阅读顺序

建议先读 `.github/workflows/node.js.yml` 和 `.github/workflows/python.yml`，因为它们直接反映代码质量门禁。读 `node.js.yml` 时，顺着看 `next/package.json`、`next/package-lock.json`、`next/prisma/useSqlite.sh`，再进入 `next/src` 和 `next/__tests__` 理解测试覆盖的业务面。

第二步读 `.github/workflows/python.yml`，再对照 `platform/pyproject.toml`、`platform/poetry.lock`、`platform/reworkd_platform`。重点看 `black`、`mypy`、`pytest` 三个 job 的差异：它们安装步骤相似，但检查目标不同；`pytest` 额外依赖 MySQL service 和环境变量，是最接近运行时行为的 CI 路径。

第三步读 `.github/workflows/webhooks.yml`。这一步不需要先理解所有业务代码，但要注意它绑定 `main`、`production` environment、仓库名判断和 secrets。它说明本仓库的生产部署可能由外部系统接管，GitHub Actions 只负责触发。

最后读 `.github/workflows/sponsors.yml`。它属于项目运营和文档自动化，优先级低于 CI 和部署，但有助于理解为什么 README 可能由机器人 PR 更新。

## 常见误区

第一个误区是把 `.github/workflows` 当成业务逻辑目录。这里没有应用入口、API 路由或核心模块，只有自动化编排。真正的 Node.js 脚本在 `next/package.json`，真正的 Python 工具配置在 `platform/pyproject.toml`。

第二个误区是以为所有 PR 都会跑全部检查。当前 workflow 使用了 `paths` 过滤：`next/**` 变更才触发 Node.js CI，`platform/**` 变更才触发 Python 检查。修改 `docs`、`cli` 或根 README 时，不一定会触发这两条代码 CI。

第三个误区是以为 `webhooks.yml` 会在任何 fork 中部署。它有 `if: github.repository == 'reworkd/AgentGPT'`，并且依赖 production environment 与 secrets；没有这些条件时，部署触发不会真正执行到外部系统。

第四个误区是忽略 working directory。`node.js.yml` 的命令默认在 `next` 下执行，`python.yml` 的命令默认在 `platform` 下执行。如果在本地复现 CI，不能直接在仓库根目录运行同名命令后就断言结果一致。

第五个误区是把 `sponsors.yml` 的 README 更新看成普通人工改动。它会定时或手动生成内容并创建 PR，因此 README 中与赞助者相关的变化可能来自自动化流程，而不是开发者直接编辑。
