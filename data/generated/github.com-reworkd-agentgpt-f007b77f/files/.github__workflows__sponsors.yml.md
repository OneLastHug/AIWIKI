# 文件：.github/workflows/sponsors.yml

## 一句话定位

`.github/workflows/sponsors.yml` 是一个 GitHub Actions 工作流，用来定时或手动刷新 `README.md` 中的赞助者展示区，并把变更以自动 PR 的形式提交回仓库。

## 它暴露/定义了什么

它定义了名为 `Generate Sponsors README` 的 CI 工作流，核心暴露的是两个触发入口和一个 `deploy` job。触发入口包括 `workflow_dispatch` 手动触发，以及 `schedule` 定时触发；定时配置为每天 UTC 00:00 执行一次。`deploy` job 运行在 `ubuntu-latest`，没有自定义脚本，而是串联多个现成 GitHub Action 完成 checkout、生成 README 赞助者列表、创建 Pull Request。

这个文件不是应用运行时代码，不参与 AgentGPT 的 Next.js、CLI 或后端逻辑。它属于仓库维护自动化，影响的是文档内容和贡献流程。

## 谁调用它

直接调用者是 GitHub Actions 平台。每天到达 `cron: 0 0 * * *` 时，GitHub 会自动调度该 workflow；仓库维护者也可以在 Actions 页面通过 `workflow_dispatch` 手动运行。

间接调用者是项目维护者和赞助数据本身：当 GitHub Sponsors 数据变化后，该工作流在下一次运行时读取赞助者信息，并尝试更新 `README.md`。根据当前片段推断，README 中的 `<!-- sponsors -->...<!-- sponsors -->` 区块是它主要维护的目标，因为 `README.md` 顶层存在该标记，中文文档 `docs/README.zh-HANS.md` 也有类似内容，但 workflow 的 `file` 参数只指向 `README.md`。

## 它调用谁

第一步调用 `actions/checkout@v2`，把仓库代码检出到 runner，后续 action 才能读取和修改文件。

第二步调用 `JamesIves/github-sponsors-readme-action@v1.2.2`。该 action 负责通过 GitHub Sponsors 相关接口获取赞助者数据，并把生成的 HTML 头像链接片段写入指定文件中的 sponsors 标记区。这里传入 `token: ${{ secrets.SPONSOR_WORKFLOW_PAT }}`、`file: 'README.md'`、`minimum: 1399`。`minimum` 根据 action 语义应是最低赞助金额或层级过滤阈值；具体单位需以该 action 文档为准，当前仓库片段只能确认它用于筛选展示对象。

第三步调用 `peter-evans/create-pull-request@v5.0.1`。它检测工作区修改，如果 `README.md` 被更新，就用同一个 PAT 创建提交和 PR，目标分支名固定为 `workflow/sponsors`，标题和提交信息为 `🤖 Update Sponsors`，标签为 `documentation`。PR body 中包含指向该 workflow 的链接，文档中不展开真实地址，记为 `[URL已移除]`。

## 核心流程

整体流程是“读赞助数据、改 README、开 PR”，而不是直接推送主分支。运行开始后，GitHub Actions 在 Ubuntu runner 上启动 `deploy` job。`checkout` 拉取当前仓库状态。随后 sponsors action 使用 `SPONSOR_WORKFLOW_PAT` 访问 GitHub API，查找项目或账号的赞助者，并定位 `README.md` 中的 sponsors 标记区域，将符合 `minimum: 1399` 条件的赞助者头像与链接片段写回该文件。最后 `create-pull-request` 检查是否产生 diff：如果没有变化，一般不会创建新的 PR；如果有变化，则在 `workflow/sponsors` 分支提交，并发起带 `documentation` 标签的 PR，等待维护者审查合并。

这个流程的设计把外部数据刷新与主分支保护隔离开：即使赞助者列表变化很频繁，也不会绕过 review 直接污染主分支文档。

## 关键函数的高层作用

该文件没有传统意义上的函数、类或模块导出，关键单元是三个 GitHub Action step。

`Checkout 🛎️` 的作用是准备仓库工作副本，属于样板步骤。

`Generate Sponsors 💖` 是核心步骤，负责根据 GitHub Sponsors 数据生成 `README.md` 的赞助者展示 HTML。它依赖 `SPONSOR_WORKFLOW_PAT`，也依赖 README 中存在可识别的 sponsors 注释标记。

`Create Pull Request` 是交付步骤，负责把上一步造成的文件修改包装成分支、commit 和 PR。它把自动化输出转化为可审查的仓库变更，是这个 workflow 与维护流程衔接的关键。

## 修改风险

最高风险是 `SPONSOR_WORKFLOW_PAT` 权限和可用性。token 缺失、过期或权限不足，会导致读取赞助者或创建 PR 失败；权限过大则增加凭据泄露后的影响面。修改时应确认该 secret 仅具备完成 sponsors 查询和 PR 创建所需的最小权限。

第二类风险是 README 标记结构。`github-sponsors-readme-action` 通常依赖 `<!-- sponsors -->` 这类边界注释来替换内容；如果手动改坏标记、删除标记或把多个标记组织得不符合 action 预期，可能导致无法更新，或替换到错误位置。仓库中 `README.md` 和部分 `docs/README.*.md` 都有 sponsors 区块，但当前 workflow 只更新 `README.md`，修改 `file` 参数时要明确是否希望同步多语言文档。

第三类风险是 action 版本。`actions/checkout@v2`、`JamesIves/github-sponsors-readme-action@v1.2.2`、`peter-evans/create-pull-request@v5.0.1` 都是固定版本。升级可能带来安全和兼容性收益，也可能改变输入参数语义、默认权限或 PR 创建行为。特别是 `minimum: 1399` 这种业务阈值，调整会直接影响哪些赞助者被展示，属于社区可见的文档策略变更。

最后，`branch: "workflow/sponsors"` 是固定分支名。如果旧 PR 长期未合并，新运行可能复用或更新同一分支；这通常便于维护，但也可能覆盖之前尚未审阅的自动更新上下文。修改分支命名策略前，需要考虑 PR 噪音、分支清理和维护者审查负担。
