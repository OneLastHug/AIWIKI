# 文件：.github/workflows/node.js.yml

## 一句话定位

`.github/workflows/node.js.yml` 是仓库中面向 `next/` 前端应用的 GitHub Actions CI 配置，用来在 `main` 分支相关的前端代码变更上自动安装依赖、运行 Jest 测试，并生成适配测试环境的 Prisma Client。

## 它暴露/定义了什么

这个文件定义了一个名为 `Node.js CI` 的 GitHub Actions workflow。它没有暴露运行时代码接口，而是暴露 CI 层面的自动化入口：

- `on.push`：当代码推送到 `main` 分支，且变更路径命中 `next/**` 时触发。
- `on.pull_request`：当面向 `main` 分支的 PR 变更命中 `next/**` 时触发。
- `jobs.build`：唯一的 CI job，运行在 `ubuntu-latest`。
- `defaults.run.working-directory: next`：所有 `run` 命令默认在 `next` 子目录执行，说明该 workflow 专门服务于仓库里的 Next.js 应用，而不是 `cli/` 或 `platform/`。

它还固定了 Node.js 运行环境为 `18.x`，这与 `next/package.json` 中 `engines.node` 的 `>=18.0.0 <19.0.0` 保持一致。

## 谁调用它

直接调用者是 GitHub Actions 平台。开发者不需要手动执行该 YAML 文件；当满足触发条件时，GitHub 会根据 `.github/workflows/node.js.yml` 创建一次 workflow run。

从仓库结构看，它与 `.github/workflows/python.yml`、`.github/workflows/webhooks.yml` 分工不同：`python.yml` 负责 `platform/**` 的 Python 测试与检查，`webhooks.yml` 负责主分支部署 webhook，而 `node.js.yml` 只覆盖 `next/**` 路径下的前端/Next.js 应用。因此根据当前片段推断，仓库采用多项目目录结构，CI 按目录边界拆分，避免无关改动触发不必要的前端测试。

## 它调用谁

该 workflow 主要调用两类对象：GitHub Actions 官方 action 和 `next/` 项目内的 npm/脚本命令。

它使用 `actions/checkout@v3` 拉取仓库源码，使用 `actions/setup-node@v3` 安装 Node.js 18，并启用 npm 缓存。缓存依赖文件指定为 `next/package-lock.json`，这说明依赖安装以 `npm` 和 lockfile 为准。

随后它在 `next` 目录内调用：

- `npm ci`：按 `next/package-lock.json` 干净安装依赖。
- `npm test`：执行 `next/package.json` 中的 `test` 脚本，也就是 `cross-env SKIP_ENV_VALIDATION=1 jest`。
- `./prisma/useSqlite.sh && npm run postinstall`：先临时把 Prisma schema 从 MySQL 调整为 SQLite 兼容形式，再执行 `postinstall`，也就是 `prisma generate`。

其中 `npm test` 会进一步读取 `next/jest.config.cjs`，通过 `next/jest` 加载 Next.js 测试配置，并使用 `jest-environment-jsdom` 作为测试环境。当前仓库中可见的测试文件包括 `next/__tests__/message-service.test.ts`、`next/__tests__/whitespace.test.ts`、`next/__tests__/with-retries.test.ts`。

## 核心流程

第一步是触发过滤。只有 `main` 分支上的 push 或面向 `main` 的 pull request，并且变更路径位于 `next/**`，才会进入这个 workflow。这种路径过滤能减少 CI 资源浪费，但也意味着如果前端依赖了仓库其他目录的共享文件，而这些文件不在 `next/**` 下，变更时不会触发该 CI。

第二步是创建 `build` job。虽然 job 名叫 `build`，但实际没有执行 `npm run build`，核心动作是安装依赖、运行测试、生成 Prisma Client。因此这里的 “build” 更像是泛化的 Node.js 校验 job，而不是生产构建校验。

第三步是准备 Node 环境。`setup-node` 使用 `18.x`，并根据 `next/package-lock.json` 建立 npm 缓存。这个设计依赖 lockfile 的稳定性，适合 CI 中使用 `npm ci`，因为 `npm ci` 会严格按 lockfile 安装，发现 `package.json` 和 lockfile 不一致时会失败。

第四步是运行测试。`npm test` 注入了一个假的 `OPENAI_API_KEY: sk-0000000000`。这不是用于真实调用 OpenAI 服务，而是为了满足应用配置或环境变量校验。`test` 脚本自身还设置了 `SKIP_ENV_VALIDATION=1`，说明测试环境会绕过一部分环境校验，以便在 CI 中只验证单元测试逻辑。

第五步是处理 Prisma。`./prisma/useSqlite.sh` 会进入 `next/prisma`，备份 `schema.prisma` 为 `schema.prisma.mysql`，然后把 datasource provider 从 `mysql` 替换为 `sqlite`，并移除若干 MySQL 专属字段标注，例如 `@db.Text`、`@db.VarChar(...)`，同时把 `Json` 替换为 `String`。随后 `npm run postinstall` 执行 `prisma generate`，基于这个被改写后的 schema 生成 Prisma Client。根据当前片段推断，这是为了让 CI 在没有 MySQL 服务的情况下仍能完成 Prisma Client 生成。

## 关键函数的高层作用

这个文件是 YAML workflow，没有传统意义上的函数或类。可以把关键配置块理解为“CI 阶段函数”：

- `on`：定义 workflow 的入口条件，相当于事件路由器，决定哪些 GitHub 事件会调用这条流水线。
- `jobs.build.defaults.run.working-directory`：定义命令执行上下文，把后续 shell 命令统一绑定到 `next` 应用目录。
- `actions/checkout@v3`：提供源码，让 CI runner 能访问仓库内容。
- `actions/setup-node@v3`：提供 Node.js 18 运行环境，并配置 npm 依赖缓存。
- `npm ci`：恢复可重复的依赖环境，是后续测试和 Prisma 生成的基础。
- `npm test`：运行 Jest 测试，是该 workflow 最重要的质量门禁。
- `prisma/useSqlite.sh` 与 `npm run postinstall`：负责把 Prisma schema 改造成 CI 可生成的版本，并执行 `prisma generate`。其中 `useSqlite.sh` 是辅助脚本，但它对数据库 provider 和字段类型做了实质性改写，风险不低。

## 修改风险

最大的风险是触发范围。当前只监听 `next/**`，如果修改了根目录 CI 相关文件、共享配置、Docker 文件或其他会影响 `next` 的跨目录资源，可能不会触发这个 workflow。相反，如果把 paths 放宽，CI 运行频率会增加。

第二个风险是 Node 版本。`node-version: 18.x` 与 `next/package.json` 的 engines 一致，随意升级到 20 或 22 可能引入依赖兼容性问题；降级则会直接违反项目声明的版本范围。

第三个风险是依赖安装方式。`npm ci` 要求 `next/package-lock.json` 与 `next/package.json` 同步。如果改成 `npm install`，CI 可重复性会下降；如果改动 `cache-dependency-path`，可能导致缓存失效或缓存错误目录。

第四个风险是测试环境变量。`OPENAI_API_KEY` 使用假值，配合 `SKIP_ENV_VALIDATION=1` 支撑测试运行。如果未来测试覆盖真实 OpenAI SDK 调用或环境校验逻辑，这个假 key 可能不再足够，测试会出现与业务无关的失败。

第五个风险是 Prisma schema 改写。`prisma/useSqlite.sh` 会直接修改 `next/prisma/schema.prisma` 工作区文件，并生成 `schema.prisma.mysql` 备份。CI runner 是一次性环境，所以通常可接受；但如果把这段脚本复用于本地或其他流水线，可能污染工作树。它还用简单文本替换处理 MySQL 到 SQLite 的差异，如果 schema 新增了复杂 MySQL 类型、Json 字段或 provider 配置，生成逻辑可能悄悄失真。

第六个风险是 job 名称与实际行为不完全一致。当前 job 叫 `build`，但没有执行 `next build`。如果维护者误以为它已经覆盖生产构建，可能漏掉 Next.js 编译期错误、类型错误或页面构建错误。若项目希望 CI 真正阻断构建失败，需要显式加入 `npm run build`，同时评估环境变量、数据库、Prisma 和 Next.js 构建依赖是否满足。
