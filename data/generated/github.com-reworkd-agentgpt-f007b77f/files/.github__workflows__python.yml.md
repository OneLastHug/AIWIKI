# 文件：.github/workflows/python.yml

## 一句话定位

`.github/workflows/python.yml` 是仓库中 `platform` Python 后端子项目的 GitHub Actions 质量门禁文件，负责在面向 `main` 分支、且改动涉及 `platform/**` 的 Pull Request 上自动执行格式检查、类型检查和测试覆盖率检查。

## 它暴露/定义了什么

该文件定义了一个名为 `Testing Platform` 的 CI workflow。它没有暴露应用层 API、函数或类，而是定义了三组独立的 GitHub Actions job：`black`、`mypy`、`pytest`。

全局环境变量只有 `PYTHON_VERSION: "3.11"`，与 `platform/pyproject.toml` 中 `python = "^3.11"` 保持一致。三个 job 都将默认执行目录设为 `platform`，说明这个 workflow 专门服务于仓库内的 Python 平台后端，而不是整个 monorepo。

它还定义了触发条件：只监听 `pull_request`，目标分支限定为 `main`，路径限定为 `platform/**`。因此，前端、文档或仓库其他目录的改动不会触发这套 Python 检查。

## 谁调用它

直接调用者是 GitHub Actions 平台。当开发者向 `main` 分支发起 Pull Request，并且 PR 中包含 `platform` 目录下的文件变更时，GitHub 会按该 YAML 文件启动 workflow。

从仓库开发流程看，它是代码合并前的自动化检查入口。开发者本地也可以参考 `platform/README.md` 中的命令手动运行同类检查，例如 `poetry run black .`、`poetry run mypy .`、`poetry run pytest -vv --cov="reworkd_platform" .`，但本文件本身只由 CI 系统解释执行。

## 它调用谁

该 workflow 主要调用三类外部能力。

第一类是 GitHub Actions 官方 action：`actions/checkout@v3` 用于拉取仓库代码，`actions/setup-python@v4` 用于安装 Python 3.11 并启用 Poetry 依赖缓存。

第二类是 Python 工具链：通过 `pipx install poetry` 安装 Poetry，再执行 `poetry install` 安装 `platform/pyproject.toml` 和 `platform/poetry.lock` 约束下的依赖。实际质量检查由 `black`、`mypy`、`pytest`、`pytest-cov` 等开发依赖完成。

第三类是测试服务依赖：`pytest` job 启动 `bitnami/mysql:8.0.30` 容器，服务名为 `reworkd_platform-db`，并映射本机 `3306` 端口。测试运行时还注入 `REWORKD_PLATFORM_HOST`、`REWORKD_PLATFORM_DB_HOST`、`REWORKD_PLATFORM_KAFKA_BOOTSTRAP_SERVERS` 等环境变量。根据当前片段推断，Kafka 没有在 CI 中实际启动，依据是 workflow 只定义了 MySQL service，却仍给测试环境提供了 Kafka bootstrap 配置。

## 核心流程

workflow 的流程分成三条并行质量线，彼此没有显式依赖关系。

`black` job 先 checkout 代码，安装 Poetry，配置 Python 3.11 和 Poetry 缓存，执行 `poetry install`，最后运行 `poetry run black --check .`。它只检查格式是否符合 Black 规则，不会自动修改代码。

`mypy` job 的初始化步骤与 `black` 基本相同，最后运行 `poetry run mypy .`。具体类型策略来自 `platform/pyproject.toml` 的 `[tool.mypy]`，其中开启了 `strict = true`，但同时允许部分动态调用和缺失 import，并排除了 `tests`。这意味着 CI 更关注业务源码的类型质量，而不是测试代码的完全类型化。

`pytest` job 在相同 Python 环境准备之外，多了 MySQL service。容器通过 `mysqladmin ping -u root` 做健康检查，最多重试 6 次。依赖安装完成后，CI 执行 `poetry run pytest -vv --cov="reworkd_platform" .`，从 `platform` 目录收集测试，并统计 `reworkd_platform` 包的覆盖率。`platform/reworkd_platform/tests` 下包含 agent、memory、settings、security、schemas 等测试文件，说明该 job 覆盖后端核心模块的单元测试与部分集成式测试。

## 关键函数的高层作用

该文件不是 Python 源码，没有函数、类或方法。这里的“关键函数”可以对应到三个关键 job。

`black` 是格式门禁，作用是防止不符合统一代码风格的 Python 代码进入主分支。它依赖 `pyproject.toml` 中 Black 版本和相关工具配置。

`mypy` 是类型门禁，作用是提前发现接口签名、返回值、可选值、泛型使用等静态类型问题。由于配置为 `strict = true`，它对业务代码的约束较强，是修改模型、服务层、API 层时的重要反馈。

`pytest` 是行为门禁，作用是运行测试套件并生成覆盖率数据。它同时承担数据库可用性校验，因为测试环境依赖 MySQL 容器和相关环境变量。辅助步骤如 `checkout`、`setup-python`、`poetry install` 属于 CI 样板准备逻辑，不承载业务判断。

## 修改风险

修改触发条件风险较高。如果放宽 `paths`，可能让无关 PR 也消耗 Python CI；如果收窄 `paths`，可能漏掉影响后端的配置或共享文件变更。当前只监听 `platform/**`，若未来有根目录配置影响 Python 项目，需要同步调整。

修改 Python 或 Poetry 版本有兼容风险。`PYTHON_VERSION` 与 `platform/pyproject.toml` 当前一致为 3.11，升级或降级都可能引发依赖解析、类型检查或运行时行为差异。

修改 `poetry install` 行为会影响三个 job 的一致性。如果改成只安装生产依赖，`black`、`mypy`、`pytest` 等开发工具可能缺失；如果依赖缓存键或 lock 文件处理不当，CI 可能出现不可复现的问题。

修改 MySQL service 风险集中在测试稳定性。数据库镜像版本、端口、用户名、库名、认证插件和健康检查参数都可能影响 `pytest` 是否能稳定连接数据库。尤其是端口固定为 `3306:3306`，在 GitHub runner 中通常可行，但迁移到自托管 runner 时可能产生冲突。

删除或弱化 `mypy`、`black`、`pytest` 任一 job 都会降低合并前反馈质量。对这个文件的安全改动通常应同时在本地执行对应命令验证，并观察 PR 上三条 CI 是否都通过。
