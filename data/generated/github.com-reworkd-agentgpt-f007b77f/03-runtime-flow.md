# 运行时流程

启动流程从部署方式开始。Docker 模式由根目录 `docker-compose.yml` 编排：`frontend` 构建 `next/Dockerfile` 并运行 Next.js，`platform` 构建 `platform/Dockerfile` 并运行 `python -m reworkd_platform`，`agentgpt_db` 提供 MySQL。手动模式由 `cli/src/index.js` 打印标题、检查 `next/.env` 是否存在、通过 Inquirer 收集配置、调用 `envGenerator.js` 写入 `next/.env` 和 `platform/.env`，或者提示分别进入 `next` 和 `platform` 启动。FastAPI 入口 `platform/reworkd_platform/__main__.py` 调用 `uvicorn.run("reworkd_platform.web.application:get_app", factory=True)`；`get_app()` 注册 CORS、lifetime、`/api` router 和平台异常处理。

配置加载分为前端与后端。Next.js 在 `next/next.config.mjs` 中导入 `next/src/env/server.mjs`，除非设置 `SKIP_ENV_VALIDATION`；server/client schema 在 `next/src/env/schema.mjs`。浏览器使用 `NEXT_PUBLIC_BACKEND_URL` 作为 FastAPI 地址，`api-utils.ts` 和 `stream-utils.ts` 都会把后端路径拼接到这个变量后。FastAPI 使用 `platform/reworkd_platform/settings.py`，Pydantic `BaseSettings` 从 `.env` 和 `REWORKD_PLATFORM_` 前缀读取 host、port、数据库、OpenAI、最大循环数、SID、Serper、Replicate 等配置。根据当前文件推断，数据库表不是在普通启动中自动创建，因为 `web/lifetime.py` 中 `_create_tables()` 被注释。

用户请求主线从 `next/src/pages/index.tsx` 开始。用户输入 goal 后触发 `handlePlay`，如果未登录则把 goal 暂存到 localStorage 并打开登录对话框；如果已登录则构造 `DefaultAgentRunModel`、`MessageService`、`AgentApi`、`AutonomousAgent`，写入 `useAgentStore` 后调用 `run()`。`AutonomousAgent` 初始 `workLog` 只有 `StartGoalWork`。它把生命周期设为 `running`，依次执行 work，执行后调用 `conclude()`，再根据 `next()` 追加后续 work；当 workLog 空时，从 `model.getCurrentTask()` 取出待执行任务并追加 `AnalyzeTaskWork`。

第一次后端调用由 `StartGoalWork.run()` 发起。它先用 `MessageService` 发送 goal message，再调用 `AgentApi.getInitialTasks()`，也就是 POST `/api/agent/start`。`AgentApi.post()` 会带上 `goal`、`model_settings` 和可选 `run_id`，并把 NextAuth session token 放入 Authorization header。FastAPI 的 `/start` 使用 `agent_start_validator`，该 validator 先通过 `AgentCRUD.create_run()` 在后端 `agent_run` 表记录 run，再通过 `get_agent_service` 创建 `OpenAIAgentService`。`start_goal_agent()` 用 `start_goal_prompt` 和 LangChain 调用模型，`TaskOutputParser` 解析出初始任务列表，响应字段为 `newTasks` 和 `run_id`。前端保存 `runId`，再调用 tRPC `agent.create` 创建可回看的 `Agent` 历史记录，并保存 goal message。

后续循环分三步。`AnalyzeTaskWork` 把当前 task 标记为 `executing`，POST `/api/agent/analyze`，后端 validator 记录一个 `analyze` 类型的 `AgentTask`，`OpenAIAgentService.analyze_task_agent()` 根据前端选择的工具名和默认工具生成 OpenAI function descriptions，让模型返回 action、reasoning、arg；解析失败时回退到默认 analysis。`ExecuteTaskWork` 随后调用 `/api/agent/execute`，该接口返回流式响应。后端根据 `analysis.action` 在 `tools.py` 中找到工具类并调用其 `call()`，例如 `Search` 搜索后总结、`Code` 运行代码 prompt、`Image` 生成图片、`SID` 查个人数据并可回退到 Search。前端 `streamText()` 逐块读取结果，持续更新 message 和 task result。`CreateTaskWork` 文件存在，`AgentApi.getAdditionalTasks()` 对应 `/api/agent/create`，但从当前 `AnalyzeTaskWork.next()` 和 `ExecuteTaskWork.next()` 看，主循环不会自动把它接到每次执行之后；是否启用需要继续查历史或改动点，因此这里标注为“根据当前文件推断”。

持久化分两条路径。前端历史由 `useAgent()` 中的 tRPC mutation 调用 `agentRouter.create` 和 `agentRouter.save`，写入 Prisma `Agent` 和 `AgentTask`；`agent/index.tsx` 可通过 `findById` 读取展示。后端 run 审计和循环限制由 validators 完成：`agent_start_validator` 创建 `AgentRun`，`validate()` 在 analyze/execute/create/summarize/chat 前创建后端 `AgentTask`，`AgentCRUD.validate_task_count()` 用 `settings.max_loops` 限制同类 step 次数，并禁止多次 summarize。聊天和总结同样走流式接口：前端 `ChatWork` POST `/api/agent/chat`，`SummarizeWork` POST `/api/agent/summarize`；后端使用 16k 模型名并通过 Lanarky `StreamingResponse.from_chain` 返回文本流。
