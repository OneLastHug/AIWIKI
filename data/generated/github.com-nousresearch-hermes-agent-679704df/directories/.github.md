# 目录：.github

## 它负责什么

`.github` 是这个仓库的 GitHub 协作与自动化控制目录，不承载 Hermes Agent 的运行时业务逻辑。它主要负责四类事情：Issue/PR 提交流程规范、GitHub Actions 复用动作、CI/发布/安全扫描工作流、Dependabot 更新策略。

从仓库整体看，Hermes Agent 的核心代码在 `run_agent.py`、`model_tools.py`、`cli.py`、`gateway/`、`tools/`、`plugins/`、`ui-tui/`、`website/` 等路径；`.github` 则围绕这些源码建立“外部守门流程”。例如 Python 测试由 `.github/workflows/tests.yml` 调用 `scripts/run_tests_parallel.py` 和 `pytest`；文档站发布由 `.github/workflows/deploy-site.yml` 调用 `website/scripts/extract-skills.py`、`website/scripts/generate-skill-docs.py` 和 Docusaurus 构建；Docker 发布由 `.github/workflows/docker-publish.yml` 构建镜像并调用 `.github/actions/hermes-smoke-test` 做基本运行冒烟检查。

这个目录体现了项目的工程治理重点：依赖和 GitHub Actions 使用 SHA 固定，Python 依赖要求上界，锁文件必须保持同步，Docker、Nix、网站、技能索引和发布链路都通过独立 workflow 管理。

## 直接子目录地图

`.github/ISSUE_TEMPLATE` 定义 GitHub Issue 表单。当前包含 bug 报告、功能请求、安装配置求助和 Issue 配置。它的作用是把用户反馈结构化，例如要求复现步骤、系统环境、`hermes debug share` 输出、受影响组件、安装方式等。`config.yml` 还配置了允许空白 Issue 和外部联系入口；文档中如需提到这些外部入口，应只写 `[URL已移除]`。

`.github/actions` 存放仓库内复用的 composite action。目前有两个关键动作：`.github/actions/hermes-smoke-test/action.yml` 和 `.github/actions/nix-setup/action.yml`。前者服务 Docker 镜像发布流程，运行镜像内真实入口的 `--help` 与 `dashboard --help`，防止镜像启动路径或 dashboard 子命令缺失。后者统一安装 Nix 并配置 Cachix 缓存，被 Nix 相关 workflow 复用。

`.github/workflows` 是 CI/CD 主目录。它包含测试、lint、Nix、Docker、文档站、技能索引、供应链审计、OSV 扫描、PyPI 发布、锁文件检查等 workflow。这里是理解仓库自动化的核心区域，但 overview 层级不需要逐个 step 展开，重点看 workflow 名称、触发条件、job 名称和调用的仓库内脚本。

## 关键入口

`.github/PULL_REQUEST_TEMPLATE.md` 是 PR 入口规范。它要求贡献者说明变更目的、关联 Issue、变更类型、测试方式和 checklist。对新增 skill 的 PR，它还单独要求确认 skill 是否适合内置、`SKILL.md` 是否符合标准格式、是否避免不必要外部依赖、是否完成端到端测试。

`.github/dependabot.yml` 是依赖更新策略入口。它明确只为 `github-actions` 开启计划更新，不为 pip/npm 源依赖做周期性自动升级。根据文件注释，这与项目供应链策略一致：源码依赖通过 `uv.lock`、`package-lock.json` 等锁文件精确固定，版本移动需要人工审查；GitHub Actions 由于也按提交 SHA 固定，因此由 Dependabot 每周提出 SHA 更新 PR。

`.github/workflows/tests.yml` 是常规测试主入口。它在 Python 代码和相关文件变化时运行，核心 job 包括分片测试和 e2e 测试。分片测试调用 `scripts/run_tests_parallel.py --slice .../6`，e2e 部分调用 `python -m pytest tests/e2e/`。

`.github/workflows/lint.yml` 是代码质量入口，覆盖 `ruff + ty diff`、阻塞式 `ruff check .` 和 Windows 兼容性风险检查。它会调用 `scripts/lint_diff.py` 和 `scripts/check-windows-footguns.py`。

`.github/workflows/upload_to_pypi.yml` 是 Python 包发布入口。它由 CalVer tag 或手动触发，构建 web dashboard、TUI bundle，把前端和安装脚本打入 wheel/sdist，然后发布到 PyPI，并使用 Sigstore 签名、附加到 GitHub Release。

`.github/workflows/docker-publish.yml` 是容器发布入口。它分别构建 amd64 与 arm64 镜像，运行 `.github/actions/hermes-smoke-test`，在发布场景下推送 digest 并合并 manifest list。

`.github/workflows/deploy-site.yml` 是网站发布入口。它构建技能索引、抽取 skill 元数据、生成 per-skill 文档页和 catalog，再构建 Docusaurus 并部署到 Pages，同时还包含一个触发外部站点部署的 job。

## 主流程位置

PR 校验主流程大致从 `.github/PULL_REQUEST_TEMPLATE.md` 开始，进入 `.github/workflows/tests.yml`、`.github/workflows/lint.yml`、`.github/workflows/uv-lockfile-check.yml`、`.github/workflows/supply-chain-audit.yml`、`.github/workflows/osv-scanner.yml` 等检查。代码变更会跑测试和 lint；依赖、锁文件或 workflow 变更会触发锁文件一致性、安全扫描和供应链规则。

发布主流程分成 Python 包、Docker 镜像和网站三条线。Python 包发布看 `.github/workflows/upload_to_pypi.yml`，它和 `scripts/release.py` 产生的 CalVer tag 有关联。Docker 发布看 `.github/workflows/docker-publish.yml`，关键复用动作在 `.github/actions/hermes-smoke-test/action.yml`。网站发布看 `.github/workflows/deploy-site.yml`，其内部衔接 `scripts/build_skills_index.py`、`website/scripts/extract-skills.py`、`website/scripts/generate-skill-docs.py`。

Nix 主流程在 `.github/workflows/nix.yml` 和 `.github/workflows/nix-lockfile-fix.yml`。前者执行 `nix flake check`、`nix build`、`nix run .#fix-lockfiles -- --check` 等校验；后者在 npm lockfile 变化后自动或按评论指令修复 `nix/tui.nix`、`nix/web.nix` 中的 hash。

技能索引相关流程分散在 `.github/workflows/skills-index.yml`、`.github/workflows/skills-index-freshness.yml` 和 `.github/workflows/deploy-site.yml`。前者定时或手动构建索引，后者检测线上索引健康度，部署流程则在网站构建时再次生成和抽取 skill 元数据。

## 推荐阅读顺序

先读 `.github/PULL_REQUEST_TEMPLATE.md`，理解维护者希望贡献者如何描述变更、测试和风险。再读 `.github/dependabot.yml`，把握这个仓库对依赖升级和供应链安全的基本态度。

接着读 `.github/workflows/tests.yml` 和 `.github/workflows/lint.yml`，这是日常 PR 最容易遇到的 CI。然后读 `.github/workflows/supply-chain-audit.yml`、`.github/workflows/uv-lockfile-check.yml`、`.github/workflows/osv-scanner.yml`，理解依赖、锁文件和安全扫描为什么会阻塞 PR。

如果关注发布，继续读 `.github/workflows/upload_to_pypi.yml`、`.github/workflows/docker-publish.yml`、`.github/workflows/deploy-site.yml`。如果关注 Nix 或前端锁文件 hash，读 `.github/workflows/nix.yml`、`.github/workflows/nix-lockfile-fix.yml` 和 `.github/actions/nix-setup/action.yml`。最后再看 `.github/ISSUE_TEMPLATE`，它更多是协作界面，不影响代码执行链路。

## 常见误区

不要把 `.github/workflows` 当成 Hermes Agent 的运行时入口。它只在 GitHub Actions 环境执行，真正的 CLI、agent loop、gateway、tool registry 和插件机制分别在 `cli.py`、`run_agent.py`、`gateway/`、`model_tools.py`、`tools/registry.py`、`plugins/` 等路径。

不要认为 Dependabot 会自动升级所有依赖。当前 `.github/dependabot.yml` 明确只处理 `github-actions`，pip/npm 依赖的常规升级不是计划型自动 PR，而是配合锁文件和人工审查推进。

不要只看 workflow 文件名就判断影响范围。很多 workflow 通过 `paths` 过滤触发，例如 Docker、网站、OSV、uv lock、docs checks 都只在相关路径变化时运行；同一个 PR 是否触发它们，取决于改动文件。

不要忽略本地 composite action。`.github/actions/hermes-smoke-test` 和 `.github/actions/nix-setup` 是多个流程背后的复用节点，排查 Docker 发布或 Nix 构建问题时，不能只看 workflow 顶层。

不要把技能索引、网站部署和 skill 文档生成混为一件事。`skills-index.yml` 负责构建索引并可触发部署；`deploy-site.yml` 会在网站构建中再次处理 skill 元数据和文档页；`skills-index-freshness.yml` 是线上健康探测。它们服务同一主题，但职责不同。
