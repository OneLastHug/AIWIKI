# 目录：.plans

## 它负责什么

`.plans` 是仓库根目录下的一个轻量级规划目录，用来保存尚未完全等同于正式文档的设计方案、功能提案和实施路线。它不是运行时代码目录，也不是构建、测试或配置入口；从当前片段看，仓库代码没有把 `.plans` 当作程序输入来扫描或加载，因此它更像开发过程中的“设计备忘区”。

当前目录只包含两个 Markdown 计划文件：` .plans/openai-api-server.md` 和 `.plans/streaming-support.md`。两者都围绕 Hermes Agent 的“外部接入”和“实时输出体验”展开：前者规划 OpenAI-compatible API Server，让外部聊天前端通过 `/v1/chat/completions`、`/v1/models` 等接口访问 Hermes；后者规划跨 CLI、Gateway、API Server 的 token-by-token streaming 支持。根据当前代码片段推断，这两个计划已经至少部分落地，因为仓库中存在 `gateway/platforms/api_server.py`、`gateway/stream_consumer.py`、`run_agent.py` 中的 `stream_delta_callback` 相关逻辑，以及对应的测试文件。

这个目录的价值在于帮助读者理解某些较大功能最初的设计意图、取舍和分阶段路线，而不是告诉你“现在代码一定长什么样”。学习时应把 `.plans` 看作架构背景材料，再回到实际实现文件验证当前状态。

## 直接子目录地图

`.plans` 当前没有直接子目录，只有两个顶层计划文档。

` .plans/openai-api-server.md`：规划 Hermes Gateway 增加 OpenAI-compatible HTTP API Server 的方案。它讨论了为什么要支持常见 OpenAI API 形状、推荐把 API Server 做成 Gateway platform adapter、请求响应格式、SSE streaming、认证、session 管理和模型映射等设计点。

` .plans/streaming-support.md`：规划 Hermes Agent 的流式输出能力。它提出通过 `stream_callback` 或类似回调机制从核心 agent 向 CLI、Gateway、API Server 等消费端传递 token delta，并要求保留非流式路径作为默认或降级路径。

因为没有更深层级，这个目录的“地图”重点不是文件树扩展，而是两个主题之间的关系：API Server 需要 OpenAI 兼容协议和 SSE 输出；Streaming Support 则提供底层 agent 到各平台的流式文本能力。二者相互补充。

## 关键入口

阅读 `.plans` 时，关键入口首先是 ` .plans/openai-api-server.md`。它从用户场景开始，说明外部 UI 如何通过 OpenAI-compatible REST API 连接 Hermes。文档中的核心建议是把 API Server 实现为 `gateway/platforms/api_server.py` 这样的 Gateway platform adapter，而不是单独绕过 Gateway 创建 agent。这个判断很重要，因为它把 API Server 纳入现有 Gateway 的 session、auth、interrupt、tool context 等体系。

第二个入口是 ` .plans/streaming-support.md`。它解释流式输出为什么应放在 `AIAgent` 的回调接口上，而不是由各个平台重复实现。文档中提到的 `run_agent.py`、`gateway/run.py`、CLI streaming display、API Server SSE 都是理解后续实现的线索。

对应到当前实现，建议把以下文件作为计划落地点的入口：`gateway/platforms/api_server.py`、`gateway/stream_consumer.py`、`run_agent.py`、`cli.py`、`gateway/run.py`、`hermes_cli/config.py`、`gateway/display_config.py`。其中 `.plans` 本身只解释设计背景，真正行为要以这些代码文件为准。

## 主流程位置

API Server 的主流程位置在 `gateway/platforms/api_server.py`。当前文件开头已经列出大量 HTTP 端点，包括 `POST /v1/chat/completions`、`POST /v1/responses`、`GET /v1/models`、`GET /v1/capabilities`、`/api/sessions`、`/v1/runs`、`/health` 等。这说明计划中的 MVP 已经扩展成更完整的 API surface。学习时可以先看该文件的 adapter 初始化、route 注册、认证检查、请求体规范化、agent 调用和 SSE 写出逻辑。

流式输出的核心流程在 `run_agent.py` 和 `gateway/stream_consumer.py`。`run_agent.py` 中的 `stream_delta_callback` 是 agent 核心向外吐出文本 delta 的关键连接点；`gateway/stream_consumer.py` 则负责把同步 agent 回调桥接到异步平台发送逻辑，处理消息编辑、完成信号、平台能力差异和失败降级。CLI 的流式显示在 `cli.py` 中，围绕 `display.streaming`、`_stream_delta`、streaming display state 等逻辑展开。

配置主流程分散在 `hermes_cli/config.py`、`gateway/display_config.py` 和 `gateway/run.py`。`hermes_cli/config.py` 提供默认配置；`gateway/display_config.py` 说明 Gateway streaming 与 CLI 的 `display.streaming` 不是同一个层级；`gateway/run.py` 中根据平台配置决定是否启用 streaming consumer，并把 callback 注入 agent。

## 推荐阅读顺序

1. 先读 ` .plans/openai-api-server.md` 的 Motivation、Architecture、Request/Response Format。目标是理解为什么 API Server 属于 Gateway adapter，以及 OpenAI-compatible 协议在这里承担什么角色。

2. 再读 ` .plans/streaming-support.md` 的 Overview、Design Principles、Architecture。重点看“callback-based”和“platform-agnostic core”两个设计原则，它们解释了为什么流式能力应从 `AIAgent` 核心向外分发。

3. 然后跳到 `gateway/platforms/api_server.py` 的文件头和路由附近。不要一开始逐行读完整文件，先建立端点地图：chat completions、responses、sessions、runs、health 分别服务什么场景。

4. 接着读 `run_agent.py` 中 `stream_delta_callback`、streaming API call、`chat()`、`run_conversation()` 附近的逻辑，确认 token delta 是怎样从模型调用路径冒出来的。

5. 最后看 `gateway/stream_consumer.py`、`gateway/run.py` 和 `cli.py` 的消费端逻辑。此时再理解“同一套 agent streaming 能力如何落到不同平台”会比较顺。

6. 如果要验证行为，读测试入口：`tests/gateway/test_api_server.py`、`tests/gateway/test_api_server_runs.py`、`tests/gateway/test_api_server_normalize.py`、`tests/run_agent/test_streaming.py`、`tests/gateway/test_stream_consumer.py`。这些测试比 `.plans` 更接近当前真实契约。

## 常见误区

第一，不要把 `.plans` 当成当前实现规范。它是计划文档，里面的阶段划分、配置名、函数名可能已经被实现时调整。比如计划里可能说 `stream_callback`，当前代码中更常见的是 `stream_delta_callback`。学习时应以代码和测试为最终依据。

第二，不要以为 `.plans` 是运行时加载目录。当前片段没有证据显示 Hermes 启动时会读取 `.plans`。它不等同于 `skills/`、`plugins/`、`gateway/platforms/` 这类会被系统发现或执行的目录。

第三，不要把 API Server 理解成完全独立的 HTTP 服务。计划文档明确推荐 Gateway Platform Adapter 路线，当前也有 `gateway/platforms/api_server.py`。这意味着它和 Gateway 的平台体系、session、工具调用、授权、streaming 逻辑有关，而不是一个简单的 FastAPI 或 aiohttp 外壳。

第四，不要把 streaming 只看成 API Server 的 SSE。`.plans/streaming-support.md` 的目标是跨平台 token streaming：CLI 可以逐字显示，Gateway 可以编辑消息或用平台原生 draft，API Server 可以输出 SSE。SSE 只是其中一种消费形式。

第五，不要忽略降级路径。两个计划都强调兼容性：非流式请求仍要可用，provider 不支持 streaming 时要回退，平台不能编辑消息时也要避免破坏最终回复。这是 Hermes 这类多平台 agent 的重要设计约束。

第六，阅读 `gateway/platforms/api_server.py` 时不要被端点数量误导。`.plans/openai-api-server.md` 描述的是最初的 OpenAI-compatible 入口；当前实现已经扩展到 Responses API、session API、runs API、capabilities 和详细 health。概览阶段应先掌握分区角色，再进入具体 handler。
