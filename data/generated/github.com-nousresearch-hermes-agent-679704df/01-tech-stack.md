# 技术栈与运行环境

`hermes-agent` 的主技术栈是 Python 3.11+。直接证据来自 `pyproject.toml` 的 `requires-python = ">=3.11"`，以及 `[project.scripts]` 中的 `hermes`、`hermes-agent`、`hermes-acp` 三个 Python 入口。核心依赖包括 `openai`、`httpx`、`rich`、`prompt_toolkit`、`tenacity`、`pyyaml`、`ruamel.yaml`、`pydantic`、`requests`、`jinja2`、`croniter`、`psutil` 等。依赖列表中的注释说明项目非常重视供应链和可复现安装：核心依赖采用精确版本，extras 用于 provider、消息平台、语音、Web、MCP、ACP 等可选能力。`uv.lock` 的存在说明开发和发布流程中使用 `uv` 锁定解析结果；`scripts/run_tests.sh` 也会优先寻找 `.venv`、`venv` 或 `$HOME/.hermes/hermes-agent/venv`。

Python 侧可以分为运行时、CLI、网关、工具、插件和测试几类依赖。`rich` 和 `prompt_toolkit` 支撑经典 CLI；`openai` 是 OpenAI-compatible API 的基础客户端；`httpx` 用于网络请求和部分异步客户端；`pydantic` 用于结构化数据；`croniter` 对应 `cron/` 调度；`psutil` 处理跨平台进程管理。`pyproject.toml` 的 optional dependencies 显示出项目按功能拆包：`messaging` 包含 Telegram、Discord、Slack、aiohttp 等；`web` 包含 `fastapi`、`uvicorn`、`starlette`，对应 dashboard 后端；`mcp`、`acp`、`voice`、`tts-premium`、`bedrock`、`azure-identity` 等是按能力加载的边缘模块。根据这些配置可以推断，默认安装尽量保持核心较小，真正使用某类后端时再启用或延迟安装相关依赖。

Node/TypeScript 不是主运行内核，但负责两个前端面。仓库根 `package.json` 只声明 `agent-browser` 依赖和 Node `>=20.0.0`，更重要的是 `ui-tui/package.json` 与 `web/package.json`。`ui-tui/` 是终端 UI，使用 `ink`、`react`、`nanostores`、`tsx`、`esbuild`、`vitest`、`eslint`、`prettier`，入口在 `ui-tui/src/entry.tsx`。它不是替代 Python Agent，而是通过 `tui_gateway/` 的 stdio JSON-RPC 与 Python 后端通信。`tui_gateway/server.py` 中将真实 stdout 保留给 JSON-RPC，并把普通 stdout 重定向到 stderr，说明协议通道对格式非常敏感。`web/` 是 Vite/React dashboard，使用 React 19、Vite 7、TypeScript、Tailwind CSS 4、xterm.js、React Router、lucide-react、Three.js 相关依赖。`web/src/pages/ChatPage.tsx`、`web/src/components/ChatSidebar.tsx`、`hermes_cli/pty_bridge.py` 和 `hermes_cli/web_server.py` 共同表明 dashboard 的聊天页围绕真实 TUI/PTY 展开，而不是重新实现完整聊天循环。

配置体系以 `~/.hermes` 为用户态根目录。`hermes_constants.py` 的 `get_hermes_home()` 是路径入口，会读取 `HERMES_HOME`，否则使用默认 Hermes home，并支持 profile 相关路径。`hermes_cli/config.py` 的文件头写明 `config.yaml` 存配置，`.env` 存 API keys 和 secrets。`DEFAULT_CONFIG` 覆盖了 `model`、`agent`、`terminal`、`compression`、`display`、`tts`、`stt`、`context`、`memory`、`delegation`、`skills`、`gateway`、`plugins` 等大类。读源码前要区分三类状态：配置状态在 `config.yaml`，秘密在 `.env`，会话历史在 `state.db`。`hermes_state.py` 说明 SQLite 状态库使用 WAL、FTS5、session source tagging、压缩后的 parent session 链等机制。

构建和测试信号也很清楚。`scripts/run_tests.sh` 是推荐测试入口，它使用干净环境、固定 `TZ=UTC`、`LANG=C.UTF-8`、`PYTHONHASHSEED=0`，并通过 `scripts/run_tests_parallel.py` 逐文件隔离运行 pytest。`pyproject.toml` 的 pytest 配置默认排除 `integration` 标记，并设置单测试超时。TypeScript 前端各自有 `npm run build`、`npm run type-check`、`npm test` 等脚本；`ui-tui` 使用 Vitest，`web` 使用 Vite 构建。Docker 侧有 `Dockerfile`、`docker-compose.yml`、`docker-compose.windows.yml`，说明项目支持容器化部署；但源码主线仍是 Python 包和 Node 前端。

读源码前需要掌握几个概念。第一，toolset 是工具集合，不等于工具实现；工具实现注册在 `tools/registry.py`，集合定义在 `toolsets.py`，最终由 `model_tools.get_tool_definitions()` 过滤。第二，provider 与 transport 分层：provider profile 描述供应商默认行为，transport/adapter 处理具体 API 形状。第三，memory 有内置 `MemoryStore` 和外部 provider plugin 两层；`agent/agent_init.py` 会根据配置初始化并把 provider 工具 schema 注入工具面。第四，context compression 是 Agent 主循环的一部分，`agent/conversation_loop.py` 会在上下文过大或 provider 报错时压缩、降级或 fallback。第五，plugin 分几类：通用插件、model-provider 插件、memory provider 插件、context/image/video/web/browser/platform 后端；它们的发现路径不同，不能假设所有插件都由同一个扫描器加载。

本项目没有单一“前端技术栈”或“后端技术栈”的简单边界。更准确地说，它是 Python Agent 核心加多个 UI/平台壳：经典 CLI、Ink TUI、dashboard、消息网关、ACP、批处理和 cron 都复用 `AIAgent`、工具注册、配置、状态库和插件机制。理解这种复用关系，比记住每个依赖名称更重要。
