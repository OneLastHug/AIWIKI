# 运行时流程

最常见的启动链从 `hermes` 命令开始。`pyproject.toml` 把 `hermes` 绑定到 `hermes_cli.main:main`。`hermes_cli/main.py` 在文件最前面尝试导入 `hermes_bootstrap`，用于 Windows UTF-8 stdio 兼容；随后处理 TUI 鼠标残留、Termux 快速版本输出、profile 预解析和日志初始化。profile 预解析很关键：`_apply_profile_override()` 会在其他 Hermes 模块导入前读取 `--profile/-p` 并设置 `HERMES_HOME`，因为配置、日志、状态库等模块可能在 import 时缓存路径。根据当前文件推断，若 profile 处理太晚，长驻进程或子进程可能写入错误的 Hermes home。

配置加载分两条常用路径。CLI 子命令和通用配置使用 `hermes_cli/config.py:load_config()`，该模块的头部说明 `~/.hermes/config.yaml` 存普通设置，`~/.hermes/.env` 存 API keys 和 secrets。`cli.py` 还有 `load_cli_config()` 一类 CLI 专用合并路径。网关运行时在 `gateway/run.py` 与 `gateway/config.py` 中有自己的读取路径。`hermes_constants.py:get_hermes_home()` 是所有这些路径的根，它读取 `HERMES_HOME`，否则回退到默认目录，并带有 profile fallback 警告。`.env` 由 `hermes_cli/env_loader.py` 加载；`tui_gateway/server.py` 和 `cli.py` 都显式调用相关加载逻辑。

进入 Agent 后，`run_agent.py:AIAgent.__init__` 只是转发到 `agent/agent_init.py:init_agent`。初始化阶段会设置模型、provider、API mode、iteration budget、callbacks、session id、platform metadata、toolsets、fallback、记忆、压缩器和 context engine。`agent/agent_init.py` 中可见它会根据 `base_url`、`provider`、模型名和配置判断 Anthropic、Bedrock、OpenAI-compatible、Codex Responses、local endpoint 等模式，并创建相应 client。随后它调用 `get_tool_definitions()`，也就是 `model_tools.py` 的主入口，按 `enabled_toolsets` 和 `disabled_toolsets` 解析工具列表。若 memory provider 或 context engine 提供额外工具 schema，初始化阶段会在去重和 gating 后注入 `agent.tools`。

工具可用性的构建流程是：`model_tools.py` import 时调用 `discover_builtin_tools()`，`tools/registry.py` 会扫描 `tools/*.py` 中顶层 `registry.register(...)` 调用并导入这些模块，导入过程完成注册。`model_tools.get_tool_definitions()` 再根据 `toolsets.py` 的定义解析需要的工具名，调用 registry 取 schema，并执行 `check_fn` 过滤不可用工具。它还会动态重写 `execute_code`、Discord、browser 等 schema，最后可能启用 `tools/tool_search.py` 的 progressive disclosure，把大量 MCP/plugin 工具折叠到搜索/描述/调用桥接工具后面。结果是 OpenAI-format 的 `{"type": "function", "function": ...}` 工具 schema。

一轮对话由 `run_agent.py:AIAgent.run_conversation()` 转发到 `agent/conversation_loop.py:run_conversation`。该文件注释说明它负责模型调用、工具派发、重试、fallback、压缩、post-turn hooks、memory/skill review nudges。流程大致如下：先恢复或构造 system prompt，把会话历史、用户消息、记忆上下文和外部 memory prefetch 组织成 messages；若上下文估算接近阈值，则触发 preflight compression；然后进入 `while (api_call_count < agent.max_iterations and agent.iteration_budget.remaining > 0) or agent._budget_grace_call` 循环。循环内准备 API messages、应用 provider 特定修正、调用模型 client，处理 streaming/non-streaming 响应，并记录 usage。

当模型返回工具调用时，Agent 不直接让模型继续，而是把 assistant tool calls 写入 messages，再执行工具。工具执行有两类：普通工具由 `model_tools.handle_function_call()` 经 `registry.dispatch()` 调用 handler；`todo`、`memory`、`session_search`、`delegate_task` 等 agent-level 工具在 Agent 循环内拦截，因为它们需要访问 Agent 的内存状态、会话库或子 Agent 预算。`model_tools.py` 还负责工具错误清洗、参数类型强制转换、pre/post tool hooks、tool result transform hooks 和结果截断。工具结果作为 `role=tool` message 回到对话，下一轮模型调用再基于结果继续。

错误与压缩路径是运行时的重要复杂度来源。`agent/conversation_loop.py` 使用 `agent/error_classifier.py` 分类 provider/API 错误，遇到 413、上下文超限、rate limit、billing/entitlement、空响应、格式错误、provider safety filter 等情况时，会在重试、压缩、credential rotation、fallback provider 之间选择路径。`agent/context_compressor.py` 或插件 context engine 负责压缩历史；`agent/agent_init.py` 会读取 `model.context_length`、custom provider context length 或自动探测结果。根据当前文件推断，项目把“长会话仍可继续”作为主循环设计重点，因此压缩和 fallback 被放进对话循环，而不是仅作为外层异常处理。

会话和数据流转主要经过 `hermes_state.py:SessionDB`。该文件说明数据库保存 session metadata、full message history、model configuration，并使用 FTS5 支持搜索。CLI、网关、TUI 都可以传入或创建 session db。消息平台路径中，`gateway/run.py` 接收 platform adapter 的 `MessageEvent`，完成鉴权、会话映射、agent cache、timeout、slash command、工具进度回调和回复发送。TUI 路径中，`ui-tui/src/gatewayClient.ts` 与 `tui_gateway/server.py` 通过 stdio JSON-RPC 通信，前端提交 `prompt.submit`，后端构造/复用 session 并发出 `message.delta`、`tool.start`、`tool.complete`、approval/clarify 等事件。dashboard 路径根据当前仓库文件推断，是 `web/` 前端调用 `hermes_cli/web_server.py`，聊天页通过 PTY bridge 嵌入真实 TUI。

计划任务路径由 `cron/` 负责。`cron/jobs.py` 把任务写入 Hermes home 下的 `cron/jobs.json`，`cron/scheduler.py` 的文件头说明 gateway 每 60 秒从后台线程调用 `tick()` 检查到期任务。计划任务会构造非交互式 Agent 运行，并且固定禁用 `cronjob`、`messaging`、`clarify` 等 toolset，防止计划任务递归创建任务或等待用户澄清。批处理路径则由 `batch_runner.py` 读取数据集、多进程运行 `AIAgent`、保存 trajectories 和工具统计，更多用于评测或训练数据生成。
